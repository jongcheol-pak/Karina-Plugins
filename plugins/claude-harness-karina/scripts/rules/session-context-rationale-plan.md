# session-context — 계획 세션 신호 판정 근거

> `session-context-rationale.md`「계획 세션·대장 신호 — 별도 문서」에서 갈라져 나왔다. §12~§21 — Deferred 대장 최고령 판정과 계획 세션 압축 리마인더의 근거를 담는다.

## 계획 세션 신호 판정 근거

## §12 ---- Deferred 대장 최고령 「마지막 판정일」

```
        # ---- Deferred 대장 최고령 「마지막 판정일」 (하네스 레포 세션에서만) ----
        # 왜: 소진 batch 착수 조건 축 ②(최고령 > 30일)가 전적으로 손계산이었고 **같은 오산이 2회** 났다
        #   — v1.188.0은 날짜 접두 부기를 못 읽어 하루 전 판정된 항목을 39일로 봤고, v1.219.0·v1.220.0은
        #   항목 안의 **최신** 스탬프를 못 읽어 34일을 보고했다(실측 14일). check-harness-consistency.py는
        #   두 문서의 문면 동기만 대조하고 **값 자체를 재는 축이 없어** 손계산이 틀려도 전 축이 통과한다.
        #   오산이 난 자리가 계획 세션(karina:plan Step 1)이라 검사기로는 늦다 — 세션 시작에 기계가 준다.
        # 판정 규칙: 항목마다 「재확인 표기·부기 형식·
        #   등록일 중 가장 최신 날짜」를 정하고 그 **최솟값**이 최고령이다.
        # **파싱 단위는 「항목」이지 「줄」이 아니다** — 대장에는 하위 불릿이 실재하고, 거기에만 최신 스탬프가
        #   붙은 항목이 생기면 줄 단위는 판정일을 **과소평가**해 축 ②를 일찍 연다(v1.188.0 오산과 같은 방향).
        # 날짜 인식을 **여는 기호 직후**(`[` 또는 `(`)로 한정하는 이유: 본문에 인용된 날짜가 섞이면 그 항목의
        #   최댓값이 밀려 올라가 최고령 후보에서 영구히 빠진다(실측: 축 ② 예정일 2026-09-18을 본문에 적은 항목).
        #   **키워드 목록으로 잡지 않는다** — 새 부기 형태를 원리상 놓친다(실측: 「실적 계측」이 목록에 없어
        #   판정 부기 하나를 놓쳤다. 이번 회차가 겨냥한 실패 유형이 바로 그것이다).
        # 미래 날짜를 후보에서 빼는 것은 위 인용 방어의 짝이다(괄호 안에 예정일이 적히는 경우).
        # (이력) 이 자리의 정규식 형태를 막던 검사기 축은 v1.224.0 에 폐지돼 지금은 형태 제약이 없다.
        # 하네스 레포 판정은 cwd 아래 plugin.json 존재이며 **상위 탐색을 하지 않는다**(아래 큐 라인과 같은 기준).
        # 전 구간 try/catch — 대장 읽기 실패가 세션 시작을 막지 않는다(fail-open).
```

## §13 종료 앵커 `^## `는 대장 끝 `## 1회 실패` 절 앞에서 대기 구간을 끊는다.

```
                # 종료 앵커 `^## `는 대장 끝 `## 1회 실패` 절 앞에서 대기 구간을 끊는다.
                #   그 절의 `- [1회 실패 …]` 줄은 날짜 접두가 아니라 끊지 않아도 세지 않는다(v1.198.0 이전엔 `## 종결` 도 있었다),
                #   주제 그룹 헤딩은 `### `라 여기 걸리지 않아 그대로 스캔된다.
```

## §14 vN 부기는 형식이 둘이다 — ⓐ 날짜 접두

```
                    # vN 부기는 **형식이 둘**이다 — ⓐ 날짜 접두(정본 ⓪이 예시하는 형태) ⓑ 제목 뒤 괄호
                    #   (v1.185.0 T2가 「부기를 제목 뒤로」 옮기는 관례를 세운 뒤의 현행 형태). 한쪽만 보면
                    #   그 축이 조용히 죽는다 — 현행 대장의 실물은 전부 ⓑ다.
```

## §15 항목이 아닌 구조 줄 — 앵커

```
                    # 항목이 아닌 **구조 줄** — 앵커(`**▶ …`)와 인용 블록(`> …`). 대장은 첫 항목 **뒤에**
                    #   이 둘이 오는 배치라, 본문으로 흡수하면 거기 적힌 날짜(카운트 기준의 실측 부기 등)가
                    #   그 항목의 판정일로 잡혀 **최고령이 실제보다 최신**이 된다 — 본문 인용 날짜를 막은 것과
                    #   같은 방향의 결함이고(batch가 늦게 열린다), 그쪽은 항목 안이라 형식 한정으로 막히지만
                    #   이쪽은 애초에 어떤 항목의 본문도 아니라 별도 필터가 필요하다.
                    #   하위 불릿(`  - …`)은 항목의 일부이므로 제외하지 않는다.
```

## §17 ---- 계획 세션의 압축 리마인더

```
        # ---- 계획 세션의 압축 리마인더 (plan이 없거나 · task 0개 · task가 전부 완료) ----
        # 위 블록은 `if ($planPath)` 안이라 **진행 중 plan이 있는 세션**만 닿는다. 계획을 세우던 중
        #   압축되면 plan이 아직 없거나 task 체크박스가 0개라 그 지시를 못 받는데, `karina:plan`도
        #   본체가 앞 5,000토큰 밖으로 밀리는 것은 같다(경계 82행 / 전체 526행 — 예산 표 실측) — Step 4 영향 범위,
        #   Step 5 작업 분해, Step 9 리뷰 게이트가 통째로 요약에 뭉개진 채 계획이 이어진다.
        # **`$open -eq 0`(전부 완료)도 대상이다.** 위 블록의 compact 재읽기 지시는 `$open -gt 0`
        #   분기에만 있고 「전부 완료」 분기(`else`)에는 없어서, **완료된 plan이 남은 채 새 계획을
        #   세우는 세션**은 두 분기 사이로 빠져 아무 재읽기 지시도 받지 못했다. 회차를 마치면 plan.md는
        #   task가 전부 [x]인 채 남고 다음 계획 세션이 그 위에서 시작하므로 이 상태가 오히려 흔하다.
        # 리마인더 줄은 plan 상태로만 분기한다(위 블록과 같은 축). 원문 발췌·조회 절차 줄은 그 위에
        #   **이 세션의 발동 기록**으로 한 번 더 거른다(2026-10-28) — 종전엔 「어느 스킬이 활성인지 알
        #   방법이 없다」며 이 분기의 모든 세션에 실었는데, 그 결과 디버깅·질문처럼 계획도 구현도 하지
        #   않은 세션이 AGENTS.md 있는 레포에서 압축될 때마다 약 12KB(계획 규칙 4,167B · 큐 규약 7,427B ·
        #   조회 절차 671B — 실측)를 받았다. 발동 기록은 이제 두 hook 이 세션 단위로 남긴다:
        #   `record-work-start.ps1` 의 `~/.claude/.state/work-start/<sid>.json` `plan` 키(plan 발동 시각)와
        #   `loop-continue.ps1` 의 `~/.claude/.state/loop-continue/<sid>.active` 마커(implement 발동이 세우고
        #   plan 발동이 지운다). 그래서 마커 유무가 plan·implement 중 **마지막 발동**을 가른다.
        #   - 계획 규칙: `plan ∧ ¬마커` — 마지막으로 한 일이 계획일 때만
        #   - 큐 규약: `마커` — 구현에 들어간 세션만(배치 시점이 구현 완료다 — §21)
        #   - 조회 절차: `plan ∨ 마커` — 그 줄이 지목하는 절이 두 스킬 것이다
        #   `chain-plan` 키는 쓰지 않는다 — 코디네이터는 인터뷰만 하고 Step 3 실측은 워커 세션의
        #   `karina:plan` 이 한다(워커는 자기 `plan` 키로 게이트를 받는다).
        #   sid 정규화(`[^A-Za-z0-9._-]` → `_`)와 상태 경로는 두 hook 의 사본이다 — 골든은 상태 파일을
        #   손으로 쓰지 않고 두 hook 을 실제로 돌려 만들어, 한쪽 경로만 바뀌면 SC41·SC42 양성이 FAIL 한다.
        # ⚠ plan도 AGENTS.md도 없는 **비 karina 프로젝트에는 붙이지 않는다** — 위 `:16` 주석의 무출력
        #   규칙과 같은 취지다. 이 리마인더는 「계획을 세우던 중이었다면」이라 대상이 karina 워크플로인데,
        #   무관한 폴더의 압축 세션에까지 뜨면 그냥 노이즈다(AGENTS.md 경로는 아래에서 다시 쓰지만
        #   여기서는 존재 판정만 필요해 직접 Test-Path 한다).
```

## §19 경로만 지시하면 읽었는지 검증할 수 없다. 계획이 추측으로 흐르는 것을 막는 절 하나만

```
            # 경로만 지시하면 읽었는지 검증할 수 없다. 계획이 추측으로 흐르는 것을 막는 절 하나만
            #   원문으로 넣는다 — 실측 3열 표가 그 자리다. 인터뷰·분해는 계획 중반이라 그때 Read해도 늦지 않다.
            # 추출 실패는 조용히 건너뛴다 — 위 경로 지시가 그대로 남아 폴백이 성립한다(구현 세션과 같은 설계).
            # 발췌는 §17 의 발동 기록 게이트(`plan ∧ ¬마커`)를 지난 세션에만 싣는다 — 게이트에 걸린
            #   세션도 추출 실패와 같은 폴백(위 경로 지시)을 받는다.
```

## §21 같은 분기에서 결정 기록 규약도 넣는다 — 구현 완료 단계의 배치 시점

```
            # 같은 분기에서 결정 기록 규약도 넣는다 — 보류·기각·번복의 배치 시점은 구현 완료 하나다
            #   (`REPO-DECISIONS.md` 「쓰기」). 이 분기의 `$open -eq 0`(task 가 전부 닫힌 plan)이 그 단계이고,
            #   karina:implement 는 그 규약을 **가리키기만 해** 압축되면 형식이 손에 남지 않는다. plan 이
            #   없거나 task 가 없는 계획 세션도 같은 분기에 들어오지만 결정을 기록하지 않는다 — 그래서
            #   2026-10-28 부터 §17 의 implement 발동 마커가 있을 때만 싣는다. 종전엔 「1줄 비용이 분기·골든을
            #   늘리는 비용보다 작다」며 가르지 않았는데, 실측 그 1줄이 7,427B 였고 무관한 압축 세션까지 받았다.
            #   2026-11-11 까지는 llm-wiki 의 vault 큐잉 절(약 7.1KB)을 실었다 — 결정 이력이
            #   레포 `docs/decisions.md` 로 옮겨 오며 형식까지 담은 「쓰기」 절(약 1.4KB)로 바꿨다.
```

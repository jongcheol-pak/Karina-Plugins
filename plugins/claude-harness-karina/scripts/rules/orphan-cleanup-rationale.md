# 고아 프로세스 회수 판정 근거

> `session-end-cleanup-lib.ps1`의 주석에서 옮긴 판정 근거다. 스크립트에는 각 자리에 이 문서의 절을 가리키는 1줄만 남겼다.
> **문면을 요약하지 않고 이동만 했다** — 이관은 이동이지 요약이 아니다.

## §1 session-end-cleanup-lib.ps1 — 고아 콘솔 프로세스 회수 함수

```
# session-end-cleanup-lib.ps1 — 고아 콘솔 프로세스 회수 함수 (dot-source 전용, 로드 시 부작용 없음)
#
# SessionEnd hook(`session-end-cleanup.ps1`)과 SessionStart hook(`session-context.ps1`)이 함께 쓴다 —
#   SessionEnd 는 크래시·강제 종료 시 발화가 보장되지 않아 세션 시작에도 같은 회수를 돌린다.
```

## §2 고아 콘솔 프로세스 회수 헬퍼

```
# ---- 고아 콘솔 프로세스 회수 헬퍼 (v1.225.0에 구 orphan-process-cleanup.ps1 을 흡수하며 삭제) ----
# session-end-cleanup-lib.ps1 — 고아 콘솔 프로세스 회수 (dot-source 전용, 로드 시 부작용 없음)
#
# 왜: Bash 도구의 시간 캡(10분)에 걸려 셸이 죽어도 그 자식 콘솔 프로세스는 함께 죽지 않는다
#   (Windows는 부모 종료 시 자식을 따라 죽이지 않고, MSYS 셸 강제 종료 시 신호도 전파되지 않는다).
#   결과로 남는 고아가 CPU를 상시 점유한다 — 2026-08-20 실측: more.com 4개가 각 74%,
#   find.exe 12개가 각 27%로 합계 코어 6개 상당을 먹고 있었다(누적 63.7 코어시간).
# 무엇을: 부모가 죽은 more.com·find.exe를 SessionStart/SessionEnd 시점에 회수한다.
#   살아 있는 셸이 쓰는 페이저·검색은 부모가 있으므로 대상이 아니다.
# 안전 계약:
#   ① 이 함수의 어떤 실패도 호출한 hook의 판정·출력에 영향을 주지 않는다(전 경로 fail-open).
#   ② 화면에 아무것도 쓰지 않는다 — 회수 사실은 hook-event-log에만 적재한다.
#      (session-context의 무출력 규약을 깨지 않기 위함이며, 골든의 ExpectSilent 케이스와도 무관해진다.)
#   ③ 5.1 호환 유지 — pwsh 7의 Process.Parent 속성을 쓰지 않고 CIM으로 부모를 조회한다.
```

## §3 회수 대상. 실측된 고아가 이 둘뿐이라 목록을 넓히지 않는다

```
# 회수 대상. 실측된 고아가 이 둘뿐이라 목록을 넓히지 않는다(오차단 위험만 늘고, 고아 조건이 이미 강한 가드다).
#
# ⚠ 이름이 두 벌인 이유 — **이름공간이 둘이고 규칙이 서로 다르다.**
#   · CIM(`Win32_Process.Name`)은 확장자를 그대로 준다      → 'more.com', 'find.exe'
#   · .NET(`Get-Process -Name` / `ProcessName`)은 **.exe만 벗긴다** → 'more.com', 'find'
#   실측: notepad은 ProcessName='Notepad'라 `-Name 'notepad.exe'`가 0건이고, more.com은 .com이
#   안 벗겨져 그대로 'more.com'이다. 한 배열을 양쪽에 쓰면 `find.exe`가 선검사에서 영원히 안 잡혀
#   **고아 find만 있을 때 조기 반환으로 회수가 통째로 죽는다**(F-7 BLOCKER 실측 — 어제 관측된 바로 그 상태).
```

```
# 골든 스위트는 hook을 실기계에서 돌리는데 프로세스는 격리 대상이 아니다.
# 이 변수가 서면 '실기계 수집' 경로만 즉시 반환한다 — 목 프로세스 목록 주입(-Processes)은 억제하지 않는다.
```

## §5 반환: 현재 부팅 세션에서 '죽지 않는다'고 확인된 PID 집합.

```
    # 반환: 현재 부팅 세션에서 '죽지 않는다'고 확인된 PID 집합.
    # 부팅 시각이 다른 마커와 30일 초과 마커는 여기서 정리한다
    # (기존 .state 자산이 예외 없이 하우스키핑을 갖는 관례 — 마커 30일·jsonl 90일).
```

부팅 표지는 v3.11.3 부터 `Win32_OperatingSystem.LastBootUpTime` 이 아니라 **수집 목록 속 PID 4(System)의 `CreationDate`** 다 — CIM 1회를 줄이려는 것이다. 두 값은 몇 초 다르지만(2026-11-12 실측 `21:19:07` 대 `21:19:04`) 한 부팅 안에서 고정이라 표지로 쓸 수 있다. 바뀐 첫 회수에서 옛 표지의 마커는 무효화되고, 갇힌 프로세스에 kill 을 한 번 더 시도한 뒤 다음 회수에서 새 표지로 다시 생긴다.

## §7 Stop-Process의 성공 반환을 소멸의 근거로 쓰지 않는다

```
                # Stop-Process의 성공 반환을 소멸의 근거로 쓰지 않는다 — 실측에서 성공을 반환하고도
                # 12/12가 살아남았다(종료 요청은 접수됐으나 커널 루프에 갇힌 상태). 재조회로 확인한다.
                # 재조회는 반드시 CIM으로 한다 — 그 상태의 프로세스는 유저 모드 객체가 이미 정리돼
                # Get-Process가 미검출하므로, 그것으로 확인하면 안 죽은 것을 죽었다고 계상한다(실측).
                # CreationDate까지 대조하는 것은 소멸 직후 같은 PID가 재할당된 경우를 가르기 위함이다.
```

v3.11.3 부터 재조회는 **같은 회수가 아니라 다음 회수의 수집 목록**이 맡는다(§9). CIM 대조라는 이 절의 요구는 그대로다.

## §8 회수 시간 예산

회수 한 번은 기본 **8000ms** 안에 끝낸다(`KARINA_ORPHAN_CLEANUP_BUDGET_MS` 로 0 이상 정수를 주면 그 값, 함수 인자 `-BudgetMs` 가 그보다 앞선다).

- **왜**: 회수는 SessionStart 묶음(timeout 20초 — `warn-version-drift` 원격 조회 최대 5초·임시 폴더 정리 2초가 함께 든다)과 SessionEnd(timeout 10초) 안에서 돈다. 묶음이 timeout 에 걸리면 디스패처가 출력을 마지막에 한 번만 내므로 AGENTS.md 주입까지 통째로 사라진다. 2026-11-12 이 기기 실측: CIM 1회 5.3~7.5초, 고아 `more.com` 1개 회수가 CIM 2N+2회로 22.5초였다.
- **어떻게**: CIM 은 남은 예산이 1000ms 이상일 때만 `-OperationTimeoutSec [floor(남은 ms / 1000)]` 를 붙여 부른다 — 이 인자는 느린 쿼리를 실제로 끊는다(1초 지정 → 1055ms 에 「시간 초과」, 실측). 1초 단위라 1000ms 미만이면 부르지 않는다. 예산 검사는 `Get-Process` 선검사보다 앞이다. `Stop-Process` 는 예산이 남았을 때만 하고, 넘으면 남은 대상은 다음 회수로 넘긴다. 어느 쪽이든 반환의 `BudgetExhausted` 가 참이다.
- **8초인 이유**: SessionEnd 10초에서 pwsh 기동분을 뺀 값이고, 느린 기기에서도 목록 CIM 1회(약 6.3초)와 선검사(약 0.25초)가 그 안에 든다.

## §9 소멸 확인은 다음 회수의 목록으로 한다

회수 한 번은 CIM 을 **1회**만 부른다 — `Win32_Process` 전체 목록 하나에서 후보·부모 생성시각·부팅 표지(§5)를 함께 얻는다. 같은 회수에서 kill 뒤 다시 조회하면 CIM 이 2회가 되어 §8 예산(느린 기기에서 약 13초)에 들지 않는다.

- **대기 기록**: kill 을 요청한 대상마다 `.claude/.state/orphan-pending/<PID>_<생성시각 ticks>_<부팅 표지>` 파일을 남긴다(본문 `name=… cpuSec=…`). 다음 회수가 목록과 대조해 **그 PID·생성시각이 없으면** `Killed` 와 `orphan-process` 이벤트로, **같은 생성시각으로 남아 있으면** `Unkillable` 과 마커(§5)로 판정하고 기록을 지운다. 그래서 이벤트는 kill 한 회수가 아니라 그다음 회수에 쌓인다.
- **대기 기록이 있으면 `Get-Process` 선검사를 건너뛴다** — 정상 소멸한 프로세스도 커널에 갇힌 프로세스(§7)도 kill 뒤에는 `Get-Process` 에 잡히지 않아, 선검사가 「대상 없음」으로 반환하면 대기가 영영 판정되지 않는다.
- **판정 순서**: 목록 → 대기 판정(마커 반영) → 대상 0건이면 반환 → 마커로 건너뛸 PID → 선택 → kill·대기 기록. 대기 판정이 「대상 0건 반환」보다 앞이어야 정상 소멸(목록에 대상 이름이 하나도 없음)을 판정한다. 마커 반영이 선택보다 앞이어야 방금 Unkillable 로 판정한 대상에 같은 회수에서 kill 을 다시 내지 않는다.
- **목록 조회가 실패·시간 초과되거나 부팅 표지를 얻지 못하면 대기를 판정하지 않고 남긴다** — 빈 목록으로 판정하면 기록 전부가 「사라짐」이 되어 갇힌 프로세스까지 회수된 것으로 센다(§7 의 취지 위반).
- **선점**: 판정 전에 기록을 `.claim` 으로 이름 바꾸고 성공한 회수만 판정한다 — 두 세션의 SessionStart·SessionEnd 가 겹쳐도 이벤트가 두 번 쌓이지 않는다. 남은 `.claim`(판정 도중 hook 이 끊긴 경우)과 대기 기록은 부팅 표지가 다르거나 30일이 지나면 판정 없이 지운다.
- **선검사 비용**: 평상시(대기 0·대상 이름 0)는 `Get-Process`(2026-11-12 실측 249ms)에서 반환해 CIM 을 부르지 않는다.

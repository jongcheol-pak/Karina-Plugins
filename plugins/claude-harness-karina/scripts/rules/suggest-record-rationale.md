# `suggest-agents-record` 판정 근거

> `suggest-agents-record.ps1`의 주석에서 옮긴 판정 근거다. 스크립트에는 각 자리에 이 문서의 절을 가리키는 1줄만 남겼다.
> **문면을 요약하지 않고 이동만 했다** — 이관은 이동이지 요약이 아니다.
> (v1.225.0 T5 에서 이관 스크립트를 두 번 돌려 이 파일이 비었던 것을 회차 시작 커밋 `6bf0fe1` 의 원문으로 복원했다.)

## §1 PostToolUse hook - PowerShell 버전

```
# PostToolUse hook - PowerShell 버전
# Bash/PowerShell 도구로 빌드·테스트·DB 명령을 실행한 뒤, 그 사실이 AGENTS.md에
# 아직 없으면 "AGENTS.md에 기록하면 다음부터 재확인 불필요"를 모델에 제안한다(비차단).
# 실제 기록은 하지 않는다 — record-project-fact 스킬이 사용자 1회 승인 후 기록한다.
#
# [설계: 왜 제안만 하고 직접 쓰지 않나]
#   AGENTS.md는 repo에 커밋되는 파일이라, 승인 없는 자동 수정은 글로벌 규칙
#   '요청 없는 파일 수정 금지'와 충돌하고 오기록이 누적될 수 있다. 따라서 이 hook은
#   감지·제안만(exit 0 비차단), 기록은 record-project-fact가 승인 게이트 뒤에서 한다.
#
# [노이즈 억제 2중]
#   (1) AGENTS.md 본문에 그 명령이 이미 있으면 제안 안 함(self-terminating).
#   (2) 세션·프로젝트·카테고리당 1회만(.state 마커).
```

**2026-11-12 부터 PostToolUse 가 아니라 셸 PreToolUse 차단 묶음의 권고 구간(`advisory:` 뒤)에서 돈다** — 위 원문의 「실행한 뒤」는 옛 배선이다. 셸 PostToolUse 블록을 지워 셸 호출당 pwsh 를 2 → 1 로 줄였다(`hook-dispatch-rationale.md` §7). 대가는 둘이다 — PostToolUse 는 성공한 호출에만 발화했는데(실패는 `PostToolUseFailure`) 이제 실패할 명령·사용자가 거부한 명령에도 제안이 나가고, 그 명령의 세션 내 1회 표지가 먼저 소모된다. 사용자 답 「Pre 로 옮기고 문구 조정」으로 감수했다: 표지는 `세션_프로젝트_종류` 단위라 다음 세션은 다시 제안하고, 표지가 30일 19개(2026-11-12 실측)일 만큼 드문 경로이며, PreToolUse 의 `additionalContext` 는 도구 결과 옆에 실려 모델이 성공 여부를 보고 판단한다. 그래서 제안 문구를 「이 명령이 성공했으면 … 물어보세요. 실패했거나 실행되지 않았으면 무시하세요」로 바꿨다. 출력 `hookEventName` 은 입력 이벤트를 따른다(없으면 `PreToolUse`).

## §2 데이터 문맥 제거: heredoc 본문은 파일 내용이지 실행 명령이 아니다

```
# ---- 데이터 문맥 제거: heredoc 본문은 파일 내용이지 실행 명령이 아니다 ----
#   `python - <<'EOF' ... EOF` 형태에서 본문에 빌드/테스트 명령 문자열이 들어 있으면 그것을
#   「이번에 실행한 명령」으로 오인한다(실측 2026-08-23 — AGENTS.md를 쓰는 heredoc 안의
#   cargo test가 제안으로 잡혔다). 셸 파서를 만들지 않고 구분자 형태만 본다 — 못 알아본 변형은
#   종전대로 전체를 훑으므로 이 제거는 오탐만 줄이고 미탐을 새로 만들지 않는다.
```

**PowerShell here-string 도 같은 데이터다** — `@'`·`@"` 로 줄이 끝나고 줄머리 `'@`·`"@` 로 닫히는 본문을 heredoc 과 같이 걷는다. 감사 세션(2026-11-07)에서 PowerShell 도구 명령의 here-string 안 `command='dotnet build'` 가 [AGENTS 기록 제안] 으로 잡혔다. 줄 중간의 `@'` 처럼 줄이 끝나지 않는 형태는 here-string 이 아니라 걷지 않는다(골든 `hooks/evals/scenarios/suggest-agents-record.ps1` 의 here-string 네 케이스).

## §3 데이터 문맥 제거 2단: 「메시지 인자」 플래그 뒤의 인용 블록도 데이터다

```
# ---- 데이터 문맥 제거 2단: 「메시지 인자」 플래그 뒤의 인용 블록도 데이터다 ----
#   `git commit -m "문서: … dotnet test 통과"`의 메시지 안 문자열이 실행 명령으로 잡혔다
#   (실측 2026-08-24 — 이 레포는 커밋 본문에 검증 명령을 적는 관례라 자주 발화한다).
#   **인용을 전부 지우면 안 된다** — `cd "경로"`의 인자가 사라져 아래 cd 게이트가 무너지고,
#   `pytest -m "not slow"`처럼 명령의 일부가 정당하게 인용된 형태도 함께 잃는다. 그래서
#   「그 자리에 실행 명령이 올 수 없는 플래그」만 화이트리스트로 잡는다.
#
#   [python 가드] `python -m <모듈>`은 -m 뒤가 실행 대상이라 지우면 미탐이 된다.
#   lookbehind로는 `python3.11`·`py -3`·`python.exe`·공백 2칸 변종을 다 덮을 수 없어
#   **python류와 `-m`의 인접**을 본다(사이에 낀 옵션은 `(-\S+\s+)*`가 흡수). 트리거를
#   「명령 어딘가에 python류가 있으면」으로 넓히면 `\bpy\b`가 `.py` 앞 마침표에서 성립해
#   `check-harness-consistency.py`를 지목하는 평범한 커밋 메시지까지 가드에 걸려,
#   이 스트립이 닫으려는 오탐이 그대로 되살아난다(실측 확인).
#
#   [무엇을 못 잡게 되는가 — 의도한 포기]
#     ① 화이트리스트 밖 형태(`echo "cargo test"` 등)의 오탐은 그대로 남는다.
#     ② 이스케이프된 중첩 인용(`-m "a \"b\" cargo test"`)은 첫 닫는 따옴표에서 끊겨 잔여가 남는다.
#     ③ 짝이 맞지 않는 따옴표는 매치되지 않아 종전 동작이다.
#     ④ 인용 안의 명령 치환(`-m "build $(npm run build)"`·백틱 형태 `` -m "build `npm run build`" ``)도
#        함께 지워진다 — 겹따옴표 안의 그 둘은 셸이 실제로 실행하므로 이것은 미탐이다(홑따옴표
#        안이면 셸도 확장하지 않아 데이터가 맞다. 스트립은 둘을 구분하지 않고 지운다 — 그 구분이
#        곧 셸 파서다).
#     ⑤ python류와 `-m`이 인접한 형태를 **메시지 안에 적으면** 가드가 걸려 그 메시지의 오탐이 남는다.
```

## §4 대상 레포 판정: 다른 폴더로 옮겨 실행한 명령은 이 프로젝트의 사실이 아니다

```
# ---- 대상 레포 판정: 다른 폴더로 옮겨 실행한 명령은 이 프로젝트의 사실이 아니다 ----
#   `cd <다른 레포> && cargo test`를 cwd의 AGENTS.md 기준으로 재면 「기록 안 됨」이 항상 참이 된다.
#   판정 불가(경로 부재·해석 실패)면 제안하지 않는다 — 여기서는 오탐이 미탐보다 비싸다.
#   줄 시작뿐 아니라 `&&`·`;`·`|` 뒤에 이어지는 cd도 본다(`npm ci && cd sub && npm test`).
#   여러 번 옮겼으면 **순서대로 누적**해 푼다 — 마지막 하나만 cwd 기준으로 풀면 2홉부터 틀린다
#   (`cd sub && cd ..`은 원래 자리로 돌아오는데 부모로 계산돼 정상 명령이 조용히 억제됐다).
#   범위 밖(정규식이 매치하지 않아 **종전 동작**으로 떨어진다): `pushd`/`popd` · 서브셸 `(cd a)`.
#   셸 파서를 만들지 않는 대가이고, 떨어지는 자리가 「제안 안 함」이 아니라 「cwd 기준 종전 판정」이라
#   미탐을 새로 만들지 않는다.
```

## §7 1회 마커는 프로젝트 경로로 가른다

```
# 폴더 이름의 비 ASCII 가 전부 `_` 가 되므로 전체 경로 해시 8자를 붙여 프로젝트마다 마커를 가른다 — 근거는 `rules/suggest-record-rationale.md` §7
```

**마커 이름은 파일명 안전 문자(`[A-Za-z0-9._-]`)만 남긴 폴더 이름을 쓰는데, 한글 폴더 이름은 글자 수만큼의 `_` 가 된다.** 그래서 같은 세션에서 글자 수가 같은 한글 폴더 두 프로젝트(`가나프로젝트`·`다라프로젝트`)가 마커를 공유해 둘째 프로젝트의 제안이 빠졌다(2026-10-30 감사).

**전체 경로(소문자)의 SHA256 앞 8자를 붙인다.** 이름은 사람이 마커 폴더를 볼 때 알아보는 용도로 남기고, 구분은 해시가 맡는다. 바뀐 이름 때문에 옛 마커는 쓰이지 않고 `session-context` 의 낡은 마커 정리가 지운다 — 업그레이드 직후 한 번 더 제안될 수 있다.

## §8 1회 표지의 성공 판정

**이 hook 은 PreToolUse 라 명령이 실행되기 전에 표지를 만든다(v3.12.0 부터).** 그대로면 실패·거부·hook 차단된 명령이 그 세션의 1회 기회를 먼저 써, 고친 뒤 성공한 같은 종류 명령에 제안이 나가지 않는다(v3.12.0 리뷰). 그래서 표지에 그 호출의 `tool_use_id` 를 `pending <id>` 로 적고, 같은 종류 명령이 다시 오면 `transcript_path` 에서 그 id 의 `tool_result` 를 찾는다.

- **`"is_error":true` 면 다시 제안하고 새 id 로 보류를 갱신한다 · 결과가 있고 `true` 가 아니면 표지를 비워 소모한다 · 결과를 아직 못 찾으면 침묵한다** — 실측(최근 transcript 200개): 실패(`Exit code`) 397 · 거부(「The user doesn't want to proceed」) 13 · hook 차단 548 이 모두 `is_error:true` 였고, 성공은 `false` 31148 이거나 필드가 없었다(33044). transcript 는 비동기로 쓰여 최근 결과가 빠질 수 있다(공식 hooks 문서) — 못 찾았을 때 다시 제안하면 성공한 명령에도 중복 제안이 나간다.
- **`"tool_use_id":"<id>"` 가 든 줄을 JSON 으로 읽어 `message.content` 의 그 id `tool_result` 객체 하나의 `is_error` 만 본다** — 실패 결과는 필드 순서가 `…"is_error":true,"tool_use_id":"<id>"}` 로 키 **앞**에 `is_error` 가 오고(최근 transcript 60개: 이 순서 281건 · 키 뒤에 `true` 0건), 성공은 키가 앞에 온다. 키 뒤 구간만 보던 첫 구현은 실데이터 실패 34건 중 33건을 성공으로 읽었다(2026-11-12 완료 리뷰 — 골든 픽스처가 실제와 다른 순서였다). 한 줄에 tool_result 가 여럿인 줄이 4583건이라 문자열 구간으로 자르면 앞 결과의 `is_error` 가 붙는다. id 는 `tool_use` 쪽에도 `"id":"<id>"` 로 나오므로 키는 `tool_use_id` 다. 그 줄에 그 id 의 `tool_result` 가 없으면(본문 인용 등) 더 앞의 같은 키를 찾는다. 줄이 창 밖에서 잘렸으면 큰 창으로 넘어가고, 5.1 의 `ConvertFrom-Json` 이 못 읽는 큰 줄이면 결과를 못 찾은 것으로 본다.
- **끝 64KB 를 먼저 읽고 없으면 끝 4MB 를 읽는다** — transcript 는 중앙값 1MB·최대 44MB 였고 보류 id 는 같은 세션의 최근 호출이다(`write-gate-trivial` 과 같은 2단계). 그 밖이면 결과를 못 찾은 것으로 보고 침묵한다.
- **입력에 `tool_use_id`·`transcript_path` 가 없으면 종전대로 첫 제안에서 바로 소모한다** — 빈 표지는 소모된 표지다(이 판정 전에 만든 표지도 같다).

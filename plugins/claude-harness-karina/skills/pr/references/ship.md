# ship — 독립 검증 PASS 뒤 merge

> `../SKILL.md` 가 ship 요청일 때 읽는다. 출처는 Cursor pstack 의 shipping 이다 — 고정 위치 `https://github.com/cursor/plugins/blob/f713f14203cd6420cec13cd7c55c32d598dbab68/pstack/skills/poteto-mode/playbooks/shipping.md`. 7번의 base 이동 영향 판정과 게이트 완화 게이트는 pstack autopilot-full 5·6단계가 출처다 — 고정 위치 `https://github.com/cursor/plugins/blob/f713f14203cd6420cec13cd7c55c32d598dbab68/pstack/skills/poteto-mode/playbooks/autopilot-full.md`. 스택 PR 은 체인 스택 착지(`../../chain-plan/references/stack-mode.md`「착지」 — 한 번에 PR 하나씩 아래부터)로만 받고, 클라우드 검증 에이전트·auto-merge·merge queue 는 들이지 않았다 — 대상은 PR 하나이고 검증자는 `pr-verifier` 서브에이전트다.

**코드를 쓰지 않은 검증자의 판정만 센다** — 작성자는 자기가 만들려던 것을 확인한다. CI 녹색과 봇 리뷰 승인은 판정이 아니다(*"Green CI and an approving bot review are not verdicts"*).

## 절차

1. **PR 을 읽는다** — `gh pr view <n> --json number,state,headRefName,headRefOid,baseRefName,baseRefOid,mergeable,mergeStateStatus,reviewDecision,title,body`. `state` 가 `OPEN` 이 아니면 멈추고 보고한다.
2. **사람의 판단이 걸려 있으면 merge 하지 않는다** — `reviewDecision` 이 `CHANGES_REQUESTED` 이거나 미해결 리뷰 스레드가 있으면(조회는 `babysit.md` 「2. 리뷰 스레드」 의 `reviewThreads` 쿼리) 「사람 판단 대기」 로 보고하고 멈춘다. 스레드를 다루는 것은 babysit(`babysit.md`)이다.
3. **PR head 와 base 를 받아 worktree 둘을 만든다** — `git fetch origin pull/<n>/head` 뒤 `git rev-parse FETCH_HEAD` 가 1번의 `headRefOid` 와 같은지 본다. 다르면 그 사이 push 가 들어온 것이니 1번부터 다시 한다. 같으면 `git worktree add --detach <스크래치 경로>/pr-<n> <headRefOid>` 로 head 를, `git fetch origin <baseRefName>` 뒤 `git worktree add --detach <스크래치 경로>/pr-<n>-base $(git merge-base <baseRefOid> <headRefOid>)` 로 base(PR 의 부모)를 받는다 — base 가 원격에서 움직였으면 `baseRefOid` 객체가 로컬에 없어 fetch 없이는 실패한다. 부모로 두는 이유는 검증자가 「PR 이 없는 같은 코드」와 대조해야 하기 때문이다 — base tip 으로 두면 그 사이 들어온 다른 PR 이 화면 시나리오를 참으로 만든다. 사용자의 체크아웃은 건드리지 않는다.
   - **만들기 전에 지난 ship 이 남긴 같은 PR 의 worktree 를 걷는다 — `git worktree prune` 뒤 `git worktree list --porcelain` 에서 이름이 `pr-<n>`·`pr-<n>-base` 이고 `detached` 인 항목을 `git worktree remove --force <경로>` 로 지우고 지운 경로를 보고에 싣는다** — 3~5번 사이에 세션이 끊기면 6번에 닿지 못해 worktree 가 남고, 스크래치 경로는 세션마다 달라 경로가 아니라 이름으로 찾아야 한다. 이름이 같아도 브랜치가 체크아웃된 worktree 는 이 스킬이 만든 것이 아니라 건드리지 않는다. 지우기에 실패하면 6번의 「worktree 미삭제」 줄로 보고하고 계속한다.
4. **`pr-verifier` 를 부른다 — 호출 전후 작업 트리 확인은 `../../READONLY-SUBAGENTS.md`「호출 전후 확인」 대로이고 재는 곳은 이 세션의 작업 트리다** — 입력은 PR 번호 · head full SHA · base 브랜치와 `baseRefOid` · head worktree 경로 · base worktree 경로와 그 SHA(부모) · 그 레포 `AGENTS.md` 경로 · 1번의 PR 본문(`body` — 본문의 `화면 시나리오:` 줄을 head 에서, `· BASE <판정>` 꼬리가 붙은 줄은 base 에서도 돌린다)이다. **PR 에 이미 달린 판정 코멘트는 merge 근거로 쓰지 않고 ship 할 때마다 새로 돌린다** — 코멘트는 로그인한 누구나 달 수 있어 작성자를 믿을 수 없다.
   - **요청에 「스택 착지」 가 있으면 먼저 `../../chain-plan/references/stack-mode.md`「착지」 의 patch-id 판정을 본다 — 같으면 3~6번을 건너뛰고 결정 기록의 그 PR 판정 줄을 4번 판정으로 쓴다. 이때 7·8번의 「4번에서 검증한 head」 는 patch-id 를 잰 지금 head(1번 `headRefOid`)이고, 「4번 때 `baseRefOid`」 는 판정 줄의 `부모` 이며, 게이트 완화·화면 게이트의 재료는 판정 줄의 `게이트 완화`·`스크린샷` 칸이다. 다르거나 판정 줄이 없으면 3번부터 그대로 돈다** — 결정 기록은 코디네이터가 계획별 검증 때 직접 쓴 레포 밖 파일이라 PR 코멘트와 달리 작성자를 안다. 착지마다 모든 PR 을 다시 검증하면 같은 패치를 두 번 잰다(2026-10-26 run_c891dfde — 착지 6 PR 재검증 2h45m).
   - **`pr-verifier` 가 판정 줄 없이 끝나면(오류·중단) 5번을 건너뛰고 6번으로 worktree 를 지운 뒤 「판정 없음」 으로 보고하고 멈춘다** — 판정이 없으면 merge 근거가 없고, 바로 멈추면 worktree 가 남는다.
5. **판정을 PR 에 기록한다** — 본문 파일을 Write 로 쓰고 `gh pr comment <n> --body-file <파일>`. 올리는 것은 판정 줄 · head SHA · base SHA · 돌린 명령 이름과 exit 코드뿐이다. 출력 원문은 로컬 보고에만 싣는다 — 공개 코멘트에 경로·시크릿이 나가지 않게 한다.
6. **worktree 둘을 지운다** — `git worktree remove <head 경로>` · `git worktree remove <base 경로>`.
   - **거부되면 그 worktree 가 3번에서 만든 것인지 확인한 뒤에만 `--force` 로 다시 지운다 — 경로가 3번의 `<스크래치 경로>/pr-<n>`(또는 `-base`)이고 `git -C <경로> rev-parse HEAD` 가 3번의 SHA 와 같아야 한다** — 거부 사유는 검증 명령이 남긴 untracked 파일·변경이고, 3번에서 만든 detached worktree 라 잃을 사용자 작업이 없다. 경로나 SHA 가 다르거나 `--force` 도 실패하면 지우지 않고 「worktree 미삭제 — <경로> · <오류 줄>」 을 보고에 싣고 7번으로 간다 — 정리 실패는 판정과 무관해 merge 를 막지 않는다. 끝에 `git worktree prune` 으로 디렉터리가 없어진 등록을 걷는다.
7. **merge 조건을 다시 본다** — 판정이 `PASS` 또는 `PASS+NOTES` 이고, `gh pr checks <n>` 이 전부 통과하고, `gh pr view <n> --json mergeable,baseRefOid` 가 `MERGEABLE` 이고 `baseRefOid` 가 4번 때와 같거나, 다르면 아래 영향 판정이 거짓이다. 판정이 `FAIL` 이면 merge 하지 않고 실패 사유를 보고한다.
   - **base 이동의 영향 판정 — `baseRefOid` 가 4번 때와 다르면 `git fetch origin <base>` 뒤 `git diff --name-only $(git merge-base <headRefOid> origin/<base>)..origin/<base>`(PR 의 부모부터 지금 base 까지)와 `gh pr diff <n> --name-only` 를 비교한다. ① 파일이 겹치거나 ② base 쪽 목록에 검증 선택 문서(`AGENTS.md`·그것이 검증 매핑으로 지목한 문서)·CI 설정(`.github/**`)·의존 매니페스트(lock·`*.csproj`·`package.json`·`requirements*`)가 있거나 ③ drift sweep(`babysit.md`「1. 충돌」 — PR 이 지우거나 옮긴 심볼의 호출부가 base diff 에 새로 있다)이 비어 있지 않으면 영향 참이다 — 참이면 merge 하지 않고 「base 합치기 필요」로 두 목록과 함께 보고하고 멈춘다(이 스킬은 브랜치를 합치지 않는다 — 체인 워커는 `../../chain-plan/references/pr-mode.md`「워커」 표대로 합치고 babysit 부터 다시 한다). 거짓이면 두 목록을 보고에 싣고 8번으로 간다. **스택 착지는 멈추지 않고 두 갈래로 간다** — 기준점은 「판정을 낸 부모 트리 → 지금 기본 브랜치」(`git diff --name-only <4번 때 baseRefOid> origin/<base>`)이고, ① 겹침이나 ② 의 검증 선택 문서·CI 설정이 있으면 그 PR 을 3번부터 다시 검증하고, ② 의 의존 매니페스트나 ③ 만 있으면 `origin/<base>` 를 detach 로 받은 검증용 worktree 에 `git merge --no-edit <headRefOid>` 한 트리에서 판정 줄의 명령을 이 세션이 다시 돌려 통과하면 8번, 실패·충돌이면 멈춘다(pstack autopilot-full 5단계)** — 검증이 돈 조합은 부모+PR 이라, base 가 그 뒤 바꾼 것 가운데 PR 이 닿는 것만 다시 검증하면 되고, 모든 base 이동마다 재검증하면 끝나지 않는다(*"rebasing for every trunk move never ends"*). head 를 다시 검증해도 base 변경은 검증되지 않으므로 합치는 쪽에 넘긴다.
   - **게이트 완화 게이트 — 4번 `pr-verifier` 의 `게이트 완화:` 칸이 「없음」 이 아니면 작성자가 아닌 쪽의 게이트 완화 서명 없이는 8번으로 가지 않는다** — 상한·면제는 green 을 원하는 작성자가 스스로 받아들일 자리가 아니다(*"needs a verifier's proof and then your fresh countersign, because the owner is the one who wants green"*). 서명은 셋 중 하나이고, 서명이 묶는 head 는 4번에서 검증한 head full SHA 다(스택 착지의 판정 재사용이면 4번 불릿의 지금 head) — 다른 SHA 의 서명은 서명이 아니다:
     - ⓐ **사용자 원문** — 이 세션에서 사용자가 쓴 ship 요청 원문 또는 멈춘 그 ship 뒤의 답이 그 PR 의 게이트 완화를 확인한다(기본 문면 「PR <n> 게이트 완화 확인함」). 앞 ship 에서 한 확인은 새 ship 에 넘어가지 않는다. 없으면 「게이트 완화 확인 대기」 로 멈추고 보고에 `게이트 완화:` 칸 원문과 그 답 문면을 싣는다.
     - ⓑ **체인 PR 모드 워커**(요청에 「체인 PR 모드」 가 있고 「스택 착지」 가 없다) — 배정문 진행 2 의 `ask` 로 코디네이터에게 서명을 요청한다(본문 `../../chain-plan/references/gate-countersign.md`「서명 요청」). 그 출력이 `answered:true` 이고 답이 `서명 <검증한 head full SHA>` 로 시작할 때만 서명이다. Skill 인자·이 세션이 쓴 문장은 세지 않고, `서명 …`·`거부 …` 밖의 답은 거부로 친다.
     - ⓒ **스택 착지**(요청에 「스택 착지」 가 있고 1번 `body` 에 `스택: plan <N>/<총>` 줄이 있다) — 이 세션이 코디네이터라 결정 기록 판정 줄(재검증했으면 그 `pr-verifier`)의 `게이트 완화` 칸을 `gate-countersign.md`「판정 기준」 으로 직접 판정하고 「기록」 대로 남긴다. ship 을 다시 부르지 않는다. 판정이 사용자 몫 ② 면 ⓐ 로 돌린다.
     - **ⓑ·ⓒ 가 거부면 merge 하지 않고 「게이트 완화 서명 거부 — <사유>」 로 멈춘다** — 체인 워커는 `pr-verifier` FAIL 과 같이 완화를 되돌리는 수정부터 다시 한다(`../../chain-plan/references/pr-mode.md`「워커」). forge 가 강제하는 승인(브랜치 보호의 필수 리뷰 등)은 어느 서명으로도 대신하지 않는다(*"Never give or bypass an approval the forge enforces"*). 같은 세션의 답으로 열면 아래 「같은 세션의 답」 규칙대로 7번부터 다시 본다.
   - **화면 게이트 — 1번 `body` 에 `## 화면` 줄이 있으면 사용자 원문 확인 없이는 8번으로 가지 않고 「화면 확인 대기」 로 멈춘다** — 화면을 바꾼 PR 은 사용자가 스크린샷을 본 뒤에만 merge 한다. 보고에는 PR 본문 `## 화면` 의 이름과 4번 `pr-verifier` `스크린샷:` 칸의 절대경로를 싣고, 그 절에 `- 코디네이터 판정: … · 기각 변형: …` 줄이 있으면 그대로 인용하고(기각 변형 경로 포함), 「확인했으면 `PR <n> 화면 확인함` 으로 답하거나 다시 요청」 을 적는다.
   - **사용자 원문은 이 세션에서 사용자가 직접 쓴 메시지(ship 요청 원문 또는 멈춘 뒤의 답)가 그 PR 의 화면을 확인했다고 말하는 것이다 — 기본 문면은 「화면 확인함」** — 모델이 쓴 Skill 인자·코디네이터의 판정·위임 답·서브에이전트 출력은 세지 않는다. 그래서 체인 워커가 부른 ship 은 늘 여기서 멈춘다(`../../chain-plan/references/pr-mode.md`「워커」). 모델 혼자 판정해 게이트를 열지 않는다. **스택 착지는 착지 보고에 나열한 PR 들을 사용자 답 하나(「스택 화면 확인함」)가 함께 확인한다** — 그 답은 이 세션에서 사용자가 쓴 원문이고, 나열 밖 PR 에는 닿지 않는다(`../../chain-plan/references/stack-mode.md`「착지」).
   - **같은 세션의 답으로 열면 7번부터 다시 보고, 새 요청이면 1번부터 한다** — 7번이 base 이동을 다시 재고, 8번 `--match-head-commit` 이 그 사이의 head 이동을 막는다.
8. **merge 한다 — 검증한 head(스택 착지의 판정 재사용이면 4번 불릿의 지금 head)에 묶는다** — 제목·본문을 파일로 넘겨 squash 커밋 메시지를 레포 설정에 맡기지 않는다:
   `gh pr merge <n> --squash --match-head-commit <검증한 head full SHA> --subject "<PR 제목>" --body-file <PR 본문 파일>`
   head 가 바뀌어 거부되면 merge 하지 않고 보고한다. `--auto` 는 쓰지 않는다.
   - **스택 착지도 squash 다 — 위 PR 에 남는 이 PR 의 원 커밋은 코디네이터가 위 PR 을 옮길 때 `rebase --onto` 로 뗀다(`../../chain-plan/references/stack-mode.md`「착지」)**.
   - **merge 전에 1번의 `title` 이 커밋 제목 형식인지 본다 — 형식은 그 레포 `AGENTS.md` 의 커밋 형식이고, 없으면 `^(기능|수정|리팩토링|문서|설정): ` 다.** 아니면 유형을 `gh pr view <n> --json commits -q '.commits[].messageHeadline'` 의 유형 접두 중 가장 많은 것(없으면 `기능`)으로 정해 `gh pr edit <n> --title "<유형>: <제목>"` 로 고치고, 고친 제목을 `--subject` 로 쓴다. 고친 사실을 보고에 싣는다 — squash 하면 이 제목이 그대로 기본 브랜치의 커밋 제목이 된다(2026-10-18 PR #3 은 손으로 열려 유형 없이 main `33d47b3d` 가 됐다).
9. **다시 읽어 확인한다** — `gh pr view <n> --json state,mergedAt,baseRefName,mergeCommit`. `state` 가 `MERGED` 이고 `baseRefName` 이 1번의 `baseRefName` 과 같아야 merge 다. 명령이 성공을 말해도 큐에 들어가기만 했거나 auto-merge 가 걸린 것은 merge 가 아니다.
10. **로컬을 맞춘다** — 작업 트리가 깨끗하면(`git status --porcelain` 빈 출력) `git switch <1번의 baseRefName>` → `git pull --ff-only`. 깨끗하지 않거나 `switch`·`pull --ff-only` 가 실패하면 하지 않고 그 사실을 보고한다.

## merge 뒤 버전 커밋

**대상 레포 `AGENTS.md` 의 Release 줄이 「merge 뒤 버전 커밋」 을 지목하고, 방금 merge 한 PR 이 그 레포가 정한 배포 대상을 바꿨으면 base 에 버전만 올린 커밋을 바로 push 한다.** 이 하니스는 하니스 루트의 런타임 폴더(`.claude-plugin agents evals hooks scripts skills`)가 배포 대상이고 버전 정본은 `.claude-plugin/plugin.json` 이다(`docs/harness-conventions.md` 「Release」). 버전 PR 을 따로 열지 않는 이유는 그 PR 이 CI·`pr-verifier` 를 한 바퀴 더 돌기 때문이고, merge 직전에 PR 에 얹지 않는 이유는 PR 이 갈라진 뒤 다른 PR 이 버전을 올렸으면 같은 버전 줄이 squash 에서 충돌하기 때문이다. **체인 PR 모드 워커는 이 절을 건너뛴다 — 버전은 체인 끝 PR 의 ship 이 한 번 올린다(`../../chain-plan/references/pr-mode.md`「P 체인 끝 PR」)**(계획 PR 은 기본 브랜치가 아닌 체인 브랜치로 merge 돼, 여기서 올리면 체인 브랜치를 건너뛰고 base 에 버전이 먼저 들어간다). 요청에 「체인 PR 모드」 가 있으면 체인 PR 모드 워커다. **스택 착지(「체인 PR 모드 · 스택 착지」)는 1번 `body` 의 `스택: plan <N>/<총>` 이 N=총인 PR 에서만 이 절을 따르고 앞 PR 은 건너뛴다** — 계획 PR 이 기본 브랜치로 바로 들어가 마지막 merge 뒤 한 번 올리면 된다(`../../chain-plan/references/stack-mode.md`「착지」).

- **10번이 `switch`·`pull --ff-only` 까지 성공했을 때만 한다** — 아니면 「버전 커밋 건너뜀 — 로컬 맞추기 실패」 를 보고에 싣는다. 사용자 체크아웃이 깨끗한 base 여야 아래 실패 경로가 그 자리로 돌아갈 수 있다.

1. `git fetch origin <base>` → `git switch --detach origin/<base>`. 로컬 base 가 아니라 detached 위에서 만드는 이유는 push 가 거부됐을 때 `git switch <base>` 하나로 버려 되돌릴 것이 없게 하려는 것이다.
2. 다음 버전을 `origin/<base>` 의 버전에서 그 레포 규약대로 정한다 — 정하지 않았으면 minor 를 1 올린다.
3. 그 레포 규약이 지목한 버전 자리만 고친다(이 레포는 `plugin.json` 의 `version` 과 `README.md` 상단 `**버전**:` 줄). **`git diff --name-only` 가 그 파일 집합과 같은지 본다** — PR·`pr-verifier` 를 거치지 않는 커밋이라 다른 변경이 섞이지 않았는지 확인할 자리가 이것뿐이다. 다르면 `git restore -- <바뀐 파일 전부>` 뒤 `git switch <base>` 로 돌아가 멈추고 보고한다.
4. `git commit -m "설정: v<버전> — <merge 한 PR 제목의 유형 뒤 요약>" -- <버전 파일>` → `git push origin HEAD:<base>`. base 에 「버전만 올린 커밋」 하나가 남아 그 위에 발행한 릴리즈 태그가 다음 판정(그 레포 규약의 태그·범위 — 이 하니스는 `git fetch -q origin tag karina-v<버전>` 뒤 `git log karina-v<버전>..HEAD -- .claude-plugin agents evals hooks scripts skills`)의 기준점이 된다.
5. **거부 출력이 non-fast-forward(`fetch first`·`non-fast-forward`)면 `git switch <base>` → `git pull --ff-only` → 1번부터 한 번만 다시 한다** — 그 사이 다른 세션이 base 에 push 했다는 뜻이라 버전을 최신 base 에서 다시 정해야 한다. **그 밖의 거부(`protected branch` 등)이거나 두 번째 거부면 detached 커밋 SHA 와 오류 줄을 보고에 적고 `git switch <base>` 로 돌아가 멈춘다** — force push 하지 않는다. 커밋은 보고된 SHA 와 reflog 로 되찾는다.
6. 성공하면 `git switch <base>` → `git pull --ff-only` 뒤 `git rev-parse HEAD` 가 push 한 커밋인지 본다. base 의 CI 는 기다리지 않는다 — 바뀐 것이 버전 문자열뿐이고 3번이 그것을 확인했다.
7. **릴리즈는 발행하지 않는다** — 태그·릴리즈는 외부·비가역이라 스킬 안에서도 별도 승인이다. 보고에 「승인 필요 — `gh release create <태그> --target <버전 커밋 full SHA>`」 를 싣는다(태그 형식은 그 레포 규약 — 이 하니스는 `karina-v<버전>` · 발행 확인은 태그가 원격에만 생겨 `gh release list`).

- 버전 자리를 고치는 편집이 plan 게이트에 막히면 `git switch <base>` 로 돌아가 버전 커밋을 건너뛰고 그 사실을 보고한다.

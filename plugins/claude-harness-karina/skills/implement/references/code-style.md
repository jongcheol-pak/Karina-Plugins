# 코드 작성 규약

> `karina:implement`의 자율 루프 2번이 **첫 코드 task 전 1회** 읽는다. 디버깅 스킬의 4-A(회귀 테스트 먼저)는 테스트 케이스 절을, 4-B(최소 수정)는 주석 절을 읽는다. `karina:no-comments` 와 그 리뷰어 `comment-reviewer` 는 주석 절을 판정 기준으로 쓰되 범위는 그 스킬이 정한다(implement 회차 끝 자동 모드도 이 절을 판정 기준으로 쓴다) — 주석 절의 hunk 범위는 implement·디버깅이 코드를 고칠 때의 것이다.
> **이 파일은 글로벌 `~/.claude/CLAUDE.md`「수정」 절이 있으면 그것을 대체하지 않고 보완한다** — 그 절을 여기 복창하지 않으며, 그 절이 없는 배포 환경에서도 여기 담은 것은 그대로 적용된다. 여기 담는 것은 **그 절이 다루지 않는, 이 하니스가 겪어서 아는 것과 다른 하니스가 겪은 것을 `[면제 ⑤ · 외부 선례]` 로 들인 것**뿐이다. **단 주석 절만은 글로벌을 셋으로 좁힌다** — ① 「수정」 절의 「딸린 주석을 갱신하거나 삭제」를 「예외면 갱신, 아니면 삭제」로 좁힌다 — 갱신과 삭제 사이를 고를 기준이 없으면 갱신으로 흘러 코드를 되풀이하는 주석이 남는다 ② 같은 문장의 대상 「딸린 주석·docstring」 을 「hunk 안 주석 + 바꾼 줄이 속한 심볼의 남길 doc 주석」 으로 좁힌다 — 정리 범위는 사용자가 hunk 로 정했다 ③ 「수정」 이 아니라 「기본 원칙」 절의 「주석·문서는 한글로 작성한다」 를 「주석의 언어는 그 파일의 기존 주석을 따른다」 로 좁힌다 — 이 하니스는 영문 주석 파일이 있는 레포에도 배포된다. **아래 「삭제 먼저」·「옛 API 정리」·「codemod 줄바꿈」 세 불릿은 글로벌 「수정」에 한 줄 원칙이 있어도 여기를 배포 환경의 정본으로 둔다** — 글로벌이 없는 배포 환경에서는 이 파일만 남는다(`../../DESIGN.md`「2. 자기참조 금지」의 의도적 이중화).
> **계획 시점의 구조 결정(파일 분할·모듈 배치·스타일 공통화·기각한 대안)은 여기가 아니다** — 그것은 `plan.md`의 각 task 에 붙는 **구조** 줄이 담고, 서식은 `../../plan/references/plan-template.md`가 정본이다.

## 확인할 수 있게 만든다

- **저장소·네트워크·파일 시스템에 닿는 코드를 판단 로직과 갈라 둔다** — 둘이 한 함수에 있으면 그 로직을 확인하는 데 그 인프라를 세워야 하고, 그러면 아무도 확인하지 않게 된다.
- **상태는 만들 때 정하고 이후 바꾸지 않는 쪽을 기본으로 한다** — 여러 곳이 같은 값을 고치면 결함이 재현되지 않는 형태로 나타나 원인을 좁히지 못한다. **다만 프레임·틱 단위로 도는 성능 경로는 예외다** — 그 자리에서는 값을 새로 만드는 비용이 문제를 옮길 뿐이다.
- **다른 값에서 계산되는 값은 저장해 동기화하지 않고 쓸 때 계산하며, 상태는 가장 좁은 범위(지역 < 필드 < 모듈 < 전역)에 둔다(파생 상태)** — 저장한 사본은 원본을 고치는 경로 하나만 동기화를 빠뜨려도 둘이 갈리고, 그 갈림은 바로 위 불릿이 말하는 재현되지 않는 결함이 된다.
- **줄 수를 줄이려고 한 줄에 조건·부수효과·반환을 겹치지 않는다** — 겹친 줄은 디버거가 멈출 자리와 스택 트레이스가 가리킬 자리를 함께 없앤다. 글로벌 「수정」의 압축 규칙이 *무엇까지 줄일 수 있는가*를 정한다면 이 줄은 *어떻게 줄이면 안 되는가*를 정한다.
- **외부 입력(요청·파일·환경·DB 행·다른 프로세스의 출력)은 경계에서 한 번 파싱해 도메인 타입으로 바꾸고, 안쪽에서는 그 타입을 믿고 다시 검증하지 않는다 — 파싱 전 데이터에는 구체 타입을 붙이지 않고, 검증 없이 타입을 단언(캐스트)하지 않는다. `isX` 류 판별 함수는 이름이 주장하는 것을 전부 확인하고, 프로젝트에 런타임 스키마 라이브러리가 있으면 손으로 쓴 검증 대신 그것을 쓴다(경계 검증)** — 검증이 안쪽에 흩어지면 어느 것이 중복인지 가를 기준이 없어 아래 「삭제 먼저」의 중복 검증을 지울 수 없고, 거짓 판별 함수는 안전하다는 이름 뒤에 결함을 숨겨 캐스트보다 찾기 어렵다. 글로벌 「품질·성능 사전 점검」의 「검증 없는 외부 입력」이 *검증하라*까지라면 이 줄은 *어디서 한 번 하고 안쪽은 믿는가*를 정한다.

## 고쳐도 무너지지 않게 만든다

- **상태를 바꾸는 명령·처리 루프는 두 번 돌거나 중간에 죽은 뒤 다시 돌아도 같은 결과로 수렴하게 한다 — 각 단계는 앞 실행이 하려던 것이 아니라 지금 있는 상태를 읽어 목표와의 차이만 적용한다. 남기는 흔적(락·임시 파일·반쯤 쓴 레코드)은 다음 실행이 낡았다고 판정할 수 있게 하되, 그 판정은 앞 실행이 어느 지점에서 멈췄어도 참인 증거로 한다(임시 경로에 쓴 뒤 rename · 생성 순서가 아니라 내용으로 비교)(멱등)** — 재시작·재시도는 정상 경로라, 앞 실행이 남긴 상태가 다음 결과를 바꾸면 재시작할 때마다 디버깅이 된다. 흔한 경우에만 맞는 표지는 멈춘 지점마다 수동 정리를 남긴다.
- **여러 주체(스레드·프로세스·세션)가 같은 대상을 쓰게 되면 먼저 대상을 나누고, 공유가 지켜야 할 불변식일 때만 락·원자적 rename·비교 후 교체(CAS) 같은 구조로 순서를 강제한다(공유 쓰기)** — 문서·규약으로 「동시에 쓰지 않는다」고 정해도 순서를 막지 못하고, 경합 결함은 재현되지 않아 사후에 원인을 좁히기 어렵다.
- **삭제 먼저** · **무언가를 더하기 전에 바꾸려는 기능이 지나는 영역(그 task 가 고치는 파일과 그 호출 경로)의 죽은 코드·중복 검증·안 쓰이는 참조를 먼저 지운다 — 기본값은 삭제이고, 레포 전체를 훑는 정리는 하지 않는다** — 더한 뒤에 지우면 새 코드가 이미 옛 잔재에 기대 있고, 지우지 않으면 다음 작업자가 죽은 경로를 살아 있는 것으로 읽는다.
- **옛 API 정리** · **새 내부 API 가 단순화·리팩토링 목적이고 프로젝트가 조율된 파괴 변경을 흡수할 수 있으면, 호환 계층을 남기지 않고 호출부를 같은 회차에 옮긴 뒤 옛 API 를 지운다 — 호출부가 plan Files 밖이어도 옮기고, 외부 소비자가 있는 API(외부에 공개된 API)의 삭제·호환을 깨는 변경만 plan 의 승인 필요 항목으로 넘긴다. 리팩토링 전의 구현 세부만 단언하던 테스트는 지우고(지운 테스트마다 무엇을 단언하던 것인지 커밋 본문에 적는다), 계약을 재는 테스트는 새 계약을 단언하게 갱신한다** — 두 경로가 남으면 다음 작업자(에이전트 포함)는 먼저 찾은 쪽을 복사해 두 경로가 함께 호출부를 늘리고, 호환 계층은 지울 날을 기다리며 영구히 남는다.
- **도메인 모델 신호** · **새 기능이 기존 if/else 사슬에 분기 하나를 더하거나 첫 boolean 과 동기화해야 하는 두 번째 boolean 을 만들거나, 변형마다 다른 필드를 선택 필드 묶음으로 표현하면, 흩어진 조건 대신 상태를 한 타입(열거·판별 유니온·상태 머신)으로 모을 신호다 — 그 타입이 분기를 줄일 때만 쓰고, 새로 쓰는 코드에 적용하며, 기존 코드는 plan 이 구조만 바꾸는 task 로 정했을 때만 이 신호로 재구성한다(목표 형태는 그 task 의 `**구조**` 줄). 언어가 지원하면 변형을 더했을 때 빠진 분기가 컴파일·린트에서 드러나게 망라 검사를 둔다. 타입을 더 좁게 강화하는 것은 느슨한 타입이 null 강제(`!`·`!!`)·캐스트·「일어날 수 없음」 예외를 강요하는 자리에서만 한다** — 조건이 흩어지면 불가능한 조합이 표현 가능해져 그 조합이 버그가 된다. 망라 검사가 없으면 새 변형은 기본 분기로 조용히 흘러간다. 줄이지 못하는 타입은 글로벌 「이 추상화를 빼면 단순해지는가」에 걸린다.

## 파일은 그 프로젝트의 관례로 저장한다

- **인코딩·줄바꿈·들여쓰기는 그 프로젝트가 문서로 정한 것(`AGENTS.md`·`.editorconfig`·`.gitattributes`)을 먼저 보고, 없으면 같은 폴더의 기존 파일을 정본으로 삼는다** — 언어와 도구 체인마다 기본값이 다르고(어떤 스택은 BOM 이 붙은 것이 정상이다), 새로 만든 파일만 다른 규약을 쓰면 그 차이가 diff 에 섞여 실제 변경을 가린다.
- **검사기 경고가 그 프로젝트 관례와 어긋나면 관례가 이긴다** — 이 하니스의 저장 규약 검사는 자기 파일 형식을 기준으로 삼으므로, 대상 프로젝트가 다른 기본값을 쓰면 그 경고는 오탐이다. 경고에 맞추려고 기존 파일과 다르게 저장하지 않는다.
- **codemod 줄바꿈** · **반복 편집은 codemod·스크립트로 하되, 파일을 바이트로 읽어 줄바꿈(CRLF/LF)·BOM 을 감지하고 같은 형식으로 쓴다 — 편집 뒤 `git diff --stat` 의 변경 줄 수가 의도와 맞는지와 `git ls-files --eol` 을 확인한다. 사소하지 않은 분석·검증(계수·잔존 확인·대조)도 눈으로 훑지 않고 다시 돌릴 수 있는 명령·스크립트로 한다 — 눈에 보이는 두세 곳짜리 확인은 면제이고, 보고에 싣는 방식은 `report-format.md`「사실 주장의 실측」이다** — 텍스트 모드 쓰기·`sed -i` 는 파일 전체의 줄바꿈을 바꿔 한 줄 수정이 전체 변경으로 보이고, 변경 줄 수가 의도보다 크면 그것이 신호다. 손으로 한 확인은 다시 하는 것 말고는 재검증할 방법이 없다.

- **케이스마다 두 편집을 떠올린다 — 동작을 깨는 편집(틀린 값을 낸다·효과를 빠뜨린다·효과를 두 번 낸다)에는 실패하고, 관측 결과를 그대로 둔 채 내부만 바꾸는 편집에는 통과해야 한다. 앞의 편집에도 통과하게 만드는 원인 넷 — 계약보다 느슨한 단언 · 대상 코드가 계산한 기대값(`../../plan/references/plan-template.md`「작업 단계」 의 「구현과 다른 축」 불릿) · 코드가 읽지 않는 상수·문구를 테스트에 다시 적은 단언 · 테스트가 직접 만든 데이터를 되읽는 단언 — 을 쓰지 않는다** — 그런 케이스는 RED→GREEN 기록을 남기고도 재는 것이 없어, 동작이 깨져도 계속 통과한다.
- **오류는 호출자가 분기하는 오류 유형(예외 타입·오류 코드)을 단언하고, 문구는 그 문구가 계약일 때(사용자에게 보이는 메시지·다른 프로그램이 파싱하는 출력)만 단언한다** — 아무도 읽지 않는 문구를 단언하면 표현만 고쳐도 깨지고, 호출자가 기대는 유형이 바뀌어도 문구가 같으면 통과한다.
- **결과가 시각·난수·실행 순서·전역 상태에 따라 갈리는 케이스는 원인을 가른다 — 원인이 우리 코드 안이면 그 값을 넣을 자리를 만들어 케이스에서 고정하고, 바꿀 수 없는 외부(OS 스케줄링·외부 서비스 타이밍)면 위 「확인할 수 있게 만든다」 첫 불릿대로 판단 로직을 갈라 그것만 케이스로 재고 경계는 원래 재현으로 본다. 재시도·sleep·느슨한 단언으로 통과를 맞추지 않고, 간헐 버그를 고정했으면 고정한 값(시드·시각·순서)을 케이스 이름이나 커밋 본문에 적는다** — 가린 비결정은 다른 순서·부하에서 다시 실패하고, 그때는 그 실패가 결함인지 흔들림인지 가를 수 없다. 고정한 값이 적혀 있지 않으면 다음 작업자는 그 케이스가 무엇을 막는지 모른다.

## 주석

- **새로 쓰거나 고치는 주석은 아래 예외 다섯과, 이 절이 정한 보존 대상, 프로젝트 규약이 요구하는 주석뿐이다** — 코드를 되풀이하는 주석은 코드가 바뀔 때 따라가지 못해 틀린 채 남고, 읽는 쪽은 코드 대신 그 주석을 믿는다.
  - 법적 고지·라이선스 헤더 — 라이선스가 요구하는 저작권·허가 고지만이다. 출처 URL 만 적은 주석은 여기 들지 않고, 출처는 커밋 본문에 적는다(번안 문서 머리말의 출처 규약 `skills/AUTHORING.md` 는 코드 주석이 아니라 대상 밖이다)
  - 바꿀 수 없는 외부 의존성·플랫폼·벤더·프로토콜이 강제해서 코드만 봐서는 알 수 없는 동작
  - 린트 억제·포매터 지시문 — 포매터 지시문(`prettier-ignore` 등)은 조건 없이 남는다. 린트 억제(`noqa`·`@ts-ignore`·`eslint-disable`·`#pragma warning disable` 등)는 그 규칙이 결함이 있거나·현학적이거나·스타일 전용일 때만 단다 — 실제 버그를 잡거나 정확성·안전을 지키는 규칙이면 억제 대신 코드를 고친다. 억제된 린트는 통과로 보고돼, 그 규칙이 잡으려던 결함이 검증을 지나간다
  - 공개 API 계약을 정의하는 doc 주석
  - 코드로 표현할 수 없는 제약을 설명하는 이슈·RFC 링크
- **우리 코드의 놀라운 동작은 주석 대신 이름·구조로 드러내고, 그래도 남는 이유는 커밋 본문에 적는다** — 이름은 코드와 함께 바뀌지만 주석은 따로 고쳐야 한다. 이 규칙은 범위 밖의 코드를 재구성할 근거가 아니다 — 구조 변경은 plan 이 정한다.
- **지켜야 할 조건(「지우지 말 것」·「바꾸기 전 X 와 상의」·「문구를 바꾸지 말 것」)은 주석으로 쓰지 않고 타입·런타임 검사·테스트·린트 중 가장 싼 것으로 강제한다 — 범위 안에서 못 하면 그 조건을 커밋 본문(커밋하지 않는 경로면 보고)에 적는다** — 주석은 아무것도 막지 않아, 그 조건을 모르는 다음 수정이 주석째 지나간다.
- **바꾼 줄과 같은 diff hunk 안(문맥 줄 포함)의 기존 주석은 예외 밖이거나 해당 여부가 확실하지 않으면 지운다 — 그 주석이 설명하던 이유가 도입 커밋 본문(`git log -S'<리터럴>'`)에 없으면 이번 커밋 본문에, 커밋하지 않는 경로면 수정 보고에 옮긴다** — 고친 코드 바로 위의 주석이 가장 먼저 낡고, 이유는 커밋 이력에서 되찾을 수 있어 지워도 정보가 사라지지 않는다.
- **hunk 밖의 주석은 건드리지 않는다** — 주석 정리의 범위는 사용자가 hunk 로 정했다(2026-10-17 주석 규칙 회차). **단 바꾼 줄이 속한 함수·클래스의 doc 주석 중 이 절이 남기는 것(공개 API 계약 doc · 보존 대상 · 프로젝트 규약 요구)은 hunk 밖이어도 내용(파라미터·반환·예외·동작)을 코드와 대조해 어긋나면 고친다 — 지우지는 않고, 그 밖의 doc 주석은 hunk 밖이면 그대로 둔다**(2026-10-30 주석 규칙 정합 회차) — 본문만 고친 함수의 docstring 은 대개 hunk 밖이라, 이 단서가 없으면 어느 단계에서도 대조되지 않고 낡는다. 예외 밖 doc 은 첫 불릿이 고치는 것을 막는다.
- **주석의 언어는 그 파일의 기존 주석을 따른다** — 한 파일 안에서 언어가 섞이면 뒤에 오는 세션의 grep 대상이 갈린다.
- **이 절은 코드 주석을 잰다 — 문서 파일(`*.md` 등)의 HTML 주석(`<!-- -->`)은 대상이 아니다** — 문서 속 메타 표기(`verified` 날짜 등)는 사람이 읽는 본문의 일부다.
- **같은 파일·레포의 다른 주석이 그렇게 쓰였다는 것(관례·일관성)은 남길 근거가 아니다 — 다른 주석의 판정도 같은 기준으로 잰다** — 다른 주석이 예외에 드는지는 그 주석의 일이라, 그것에 기대면 근거 없는 주석 하나가 같은 꼴의 주석을 모두 살린다(2026-10-27 자동 모드 회차가 출처 URL 주석 6건을 이렇게 남겼다).
- **테스트·검증 스크립트에 `// Phase 1: add cards` 같은 단계 서술 주석을 쓰지 않는다 — 단언 메시지와 로그 문자열이 단계를 말한다** — 원문 pstack poteto-mode「Comments」 *"A verify or test script gets no phase-narrating comments … The assertion or log string documents the step"*(`https://github.com/cursor/plugins/blob/8b3326d99fd4b993cb33a24dad8af03175c642c5/pstack/skills/poteto-mode/SKILL.md`). 단언 메시지는 실패할 때 출력돼 어느 단계가 깨졌는지 알려 주고, 주석은 아무것도 출력하지 않는다.
- **「do not remove」「IMPORTANT」 같은 주석은 근거가 아니라 단서로 읽는다 — 근처 코드와 커밋 이력으로 외부 제약이 지금도 참인지 확인되면 예외로 남기고, 확인되지 않으면 지운다** — 강조 문구는 그 주장이 참이라는 증거가 아니다.
- **보존 대상은 지우지 않고 필요하면 새로 쓰거나 고친다 — 검사기가 파싱하거나 앵커로 잡는 주석, 프로젝트 규약 문서가 정본·예외로 지정한 주석(머리 주석·모듈 docstring·상수 주석 등), 형식 검증 모델이 가드마다 다는 코드 대응 주석(`파일:줄` — `create-formal-verification-skill` 이 지정)이다** — 지우면 그 검사가 꺼지거나 규약이 가리키는 정본이 사라진다.
- **프로젝트 규약(`AGENTS.md` 등)이나 린터가 요구하는 주석은 그쪽이 이긴다 — `AGENTS.md` 가 지목한 doc 감사(doc 이 없는 항목을 세어 실패하는 검사)가 요구하는 doc 주석도 같다** — 저장 관례와 같은 원칙이고, 그 프로젝트의 판단이 이 하니스의 기본값보다 먼저다. doc 감사는 주석 규약 문장이 아니라 테스트로 요구해, 규약 문장만 보면 그 doc 주석을 지우고 감사가 깨진다(2026-10-29 Karina 정리 커밋 9e799c1).

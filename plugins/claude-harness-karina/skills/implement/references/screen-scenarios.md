# 화면 시나리오 실행 · 「확인할 것」 화면 행

> `report-format.md` 에서 떼어 낸 조건부 참조다 — plan 에 `**화면**` 줄이 있거나, 앱 조작으로 화면을 확인하거나, 사용자에게 스크린샷을 보이는 보고(「확인할 것」 표의 화면 행)를 낼 때만 읽는다. 「화면 시나리오 실행」 은 루프 중 앱 조작 시점에도 읽힌다.

## 화면 시나리오 실행

**task 에 `**화면**` 줄(서식 `../../plan/references/plan-template.md`「작업 단계」)이 있으면 `AGENTS.md` 의 `Verify (앱 조작)` 줄이 가리키는 검증 스킬로 그 시나리오를 HEAD 에서 돌리고, 스크린샷을 그 스킬의 Evidence 위치에 줄에 적힌 이름으로 남겨 통과 조건으로 판정한다.** 순서는 그 스킬의 Launch → Doctor → Drive → Evidence → Cleanup 이고, 증거 기준은 `report-format.md`「사실 주장의 실측」 이다. 계획 시점에 정한 시나리오를 그대로 돌려야 실행 시점의 즉흥 설계가 판정을 대신하지 않는다.

- **task 루프의 화면 시나리오(회차 끝에 모아 도는 것 포함)는 메인 세션이 직접 돌리고 서브에이전트에 맡기지 않는다** — 맡기면 서브에이전트가 맥락을 다시 읽고 앱 기동·정리를 되풀이하는 동안 메인은 시한 없이 대기만 한다(2026-11-12 Karina 체인 plan 7 — 52분, 도구 호출 297회).
- **화면 판정을 모아 돌 때는 회차 끝까지 미루지 않고 묶음으로 끊는다 — 화면 task 5개가 쌓이면, 또는 오버레이·위치 계산을 새로 만드는 task 를 끝낸 직후에 그때까지의 묶음을 돈다. 「회차 끝」 으로 미룬 Acceptance 실기(화면 줄 밖의 앱 조작 확인)도 같은 묶음 목록에 넣어 함께 돈다** — 묶음이 크면 결함이 한자리에 몰려 건마다 RED·GREEN·재기동 컴파일(회당 4~9분)을 따로 치르고, 목록 밖에 둔 실기는 빠진다(2026-11-19 Karina 체인 run_c5849ef7 plan 9 — 화면 task 20개를 회차 끝에 모아 결함 11건이 몰렸고, 회차 끝으로 미룬 T17 실기가 빠져 완료 리뷰 BLOCKER).
- **시나리오는 HEAD 한 쪽에서만 돈다 — BASE 를 따로 받아 같은 화면을 다시 돌지 않는다** — BASE 빌드·조작이 회차마다 분 단위를 더했고, 같은 화면을 루프·BASE·게이트에서 최대 네 번 돌았다(사용자 답 「BASE 화면 재실행 완전 제거」 2026-11-14). 예외는 통과 조건이 `기준선 일치` 인 task 의 편집 전 기준선 하나다(아래).
- **검증 스킬을 Launch 하기 전마다 화면 가리기를 걷는다 — `../../SCREEN-COVER.md`「언제 끄고 켜는가」(보유자 `implement:<레포 루트>`). 다시 덮는 것은 task 마다가 아니라 회차 끝 「소요 기록」 과, 회차 중간에 멈추는 보고 직전이다** — 가리기가 켜진 모니터는 마우스 입력이 막혀 조작이 실패하고, task 사이에 덮으면 다음 task 의 조작이 다시 막힌다.
- **검증 스킬이 없으면(`Verify (앱 조작)` 줄이 없거나 「없음」) 화면 줄을 그대로 HUMAN-VERIFY 로 옮기고, 커밋 본문에 `화면: 미촬영(HUMAN-VERIFY) · 스크린샷 <이름> · 시나리오 <조작 순서> · 통과 조건 <조건>` 줄을 남긴다** — 시나리오·스크린샷 이름·통과 조건을 그대로 적어야 사용자가 같은 것을 돌린다. 커밋 줄이 없으면 체인 보고가 화면 task 를 찾지 못한다. 통과 조건이 `기준선 일치` 면 기준선을 찍지 않고 사유 칸에 `BASE <sha7> 와 HEAD 에서 같은 화면을 찍어 pwsh -NoProfile -File "<implement 스킬 폴더>/scripts/image-diff.ps1" -Base <BASE 화면> -Head <HEAD 화면> [-Mask <계획의 가림>] 로 비교` 를 적는다 — 사용자가 눈 대조 대신 같은 판정기를 돌린다.
- **참/거짓을 적기 전에 남긴 스크린샷을 Read 로 열어 통과 조건과 대조한다 — 검증 스킬 출력·로그 문구만으로 판정하지 않는다** — 스킬이 「성공」 을 내도 화면이 통과 조건과 다를 수 있고, 이미지를 직접 보는 것만 그 차이를 잡는다(pstack guide 06 *"Ask for the proof as an artifact you can inspect yourself"* — `https://github.com/cursor/plugins/blob/ae5650febf4320793844c12c4adaa937f417f8da/pstack/docs/guide/06-verify-and-ship.md`).
- **조작 실패가 검증 스킬 헬퍼·시나리오의 수단 결함이면(헬퍼 오류·낡은 선택자·틀린 기동 절차) 미촬영으로 닫지 않고 그 헬퍼·시나리오를 고쳐 다시 돌린다 — `loop-exceptions.md`「검증 수단 결함」 · 「레포 문서·스크립트 정정」** — 고장 난 헬퍼를 사유로 넘기면 다음 회차도 같은 자리에서 미촬영이 된다.
- **검증 스킬이 있는데 수단을 고친 뒤에도 조작이 끝내 실패하면(앱·환경 사유의 기동 실패·요소 못 찾음) `화면: 미촬영(HUMAN-VERIFY) · 스크린샷 <이름> · 시나리오 <조작 순서> · 통과 조건 <조건> · 사유 <조작 실패 요지>` 줄을 커밋 본문에 남긴다** — 판정 줄이 없으면 회차 끝 증거 대조가 `no-screen-verdict` 로 막고, 사유 칸이 있어야 그 미촬영이 위반이 아니라 note 로 읽힌다(`../../plan/scripts/check-plan.ps1` 머리 주석).
- **판정은 둘이다(조작이 끝내 실패한 경우는 위 미촬영 줄) — HEAD 에서 통과 조건이 참이면 통과(`[x]`), 거짓이면 그 task 의 검증 실패다(`loop-exceptions.md`「실패 처리」)** — 통과 조건이 변경 전에도 참일 수 있는 시나리오는 계획이 통과 조건을 변경이 만드는 상태로 적어 가른다(`../../plan/references/plan-template.md`「작업 단계」). `기준선 일치` 는 변경 전 기준선과 비교하므로 이 문장의 예외이고 판정은 아래 불릿이다.
- **통과 조건이 `기준선 일치` 면 그 task 의 파일을 고치기 전에 같은 작업 트리에서 같은 시나리오를 돌려 `base-<이름>` 을 찍고, 찍은 뒤에는 고치지 않으며, Progress Log 에 `기준선: <이름> — HEAD <sha7> · task 파일 미수정` 줄을 남긴다 — BASE 빌드·worktree 는 쓰지 않는다(검증 스킬이 있는 레포의 `git worktree add` 에는 `guard-bash` 가 이 줄을 경고로 띄운다)** — 고친 뒤에 찍은 기준선은 HEAD 와 같아 diff 가 늘 0 이고, 기록이 없으면 언제 찍었는지 갈리지 않는다(pstack visual parity *"The baseline is the spec. You do not touch it."* — `https://github.com/cursor/plugins/blob/ae5650febf4320793844c12c4adaa937f417f8da/pstack/skills/poteto-mode/playbooks/visual-parity.md`).
- **기준선은 계획의 `T<N>-1` 에서 찍는다. 찍은 뒤 Cleanup → Launch 부터 시나리오를 한 번 더 돌려 `base2-<이름>` 을 찍고 `image-diff.ps1 -Base <base-<이름>> -Head <base2-<이름>> [-Mask <계획의 가림>] -Out <diff-base2-<이름>>` 로 비교한다 — exit 1 이면 HEAD 를 찍지 않고 그 화면만 미촬영 줄(사유 `기준선 흔들림 <N> px bbox <x,y,w,h>`, 크기가 다르면 `기준선 흔들림 size <…>`)로 남기고 루프는 계속하며, exit 2 면 사유에 그 `ERROR` 를 싣는다. `base2-<이름>`·`diff-base2-<이름>` 도 `화면 경로:` 줄에 남긴다** — 편집 없이도 갈리는 영역(시계·커서·애니메이션)이 있으면 HEAD diff 가 변경 탓인지 갈리지 않고, bbox 가 계획에 더할 가림 후보다.
- **HEAD 의 `<이름>` 을 찍은 뒤 `pwsh -NoProfile -File "<implement 스킬 폴더>/scripts/image-diff.ps1" -Base <base-<이름>> -Head <<이름>> [-Mask 'x,y,w,h;…'] -Out <diff-<이름>>` 로 판정한다 — 첫 줄 `image-diff: diff <N> px of <W>x<H>`(가림이 있으면 ` masked <M> px`, 가림 밖 diff 가 0 이 아니면 끝에 ` bbox <x>,<y>,<w>,<h>`) 와 exit 0 이면 참, `diff` 가 0 이 아니거나 `image-diff: size …` 로 exit 1 이면 거짓, `image-diff: ERROR …` 로 exit 2 면 미촬영 줄의 사유다. 가림은 계획 통과 조건의 `(가림 …)` 그대로이고, 이미지 밖으로 나가면 잘라 쓰지 않고 exit 2 다(DPI 가 다른 PC 의 좌표 어긋남)** — 눈 대조는 1px 이동·색 차이를 통과시킨다(*"Equivalence is verified by image diff, not by eye."* — 같은 출처).
- **diff 가 0 이어도 `<이름>` 을 Read 로 연다 — 거짓이면 `diff-<이름>`(다른 픽셀을 빨강으로 칠한 사본)도 연다. 판정 줄 통과 조건 칸은 `기준선 일치(diff <N> px)` 이고, Progress Log `화면 경로:` 줄은 `base-<이름>`·`diff-<이름>` 도 남긴다** — 기준선 자체가 기동 실패 화면이면 두 장이 같아 0 이 나온다.
- **커밋 본문에 판정 한 줄을 남긴다 — `화면: HEAD <참|거짓> · 스크린샷 <이름> · 시나리오 <조작 순서> · 통과 조건 <조건>`** — 완료 리뷰가 이 줄로 시나리오를 돌렸는지 대조하고, 체인 보고와 다음 세션이 `git log` 에서 화면 task 를 찾는다.
- **모아 돈 묶음의 화면은 묶음마다 커밋 하나에 남긴다 — 제목 `{유형}: 화면 일괄 판정 — T<N>·T<M>…`, 본문에 화면마다 task 를 지목한 `화면: T<N> HEAD <참|거짓> · …`·`화면: T<N> 미촬영(HUMAN-VERIFY) · … · 사유 <…>` 줄** — 증거 대조(`check-plan.ps1 -Base`)가 BASE..HEAD 어느 커밋이든 지목 줄을 그 task 의 화면 판정으로 받는다. 제목에서 유형 바로 뒤에 `T<N>` 을 두지 않는다 — 그러면 `guard-bash` 가 완료 커밋으로 읽어 그 task 체크박스를 요구한다. 지목 줄은 task 완료 커밋·`검증 결과:` 를 대신하지 않는다.
- **시나리오·통과 조건 칸에는 ` · ` 를 쓰지 않는다 — 단계는 `→` 로 잇는다** — 칸 구분자가 ` · ` 라, 칸 안에 쓰면 칸이 어디서 끝나는지 가를 근거가 칸 이름뿐이다.
- **남긴 스크린샷마다 `## Progress Log` 에 `화면 경로: <이름> — <경로>` 한 줄을 남긴다 — 경로의 사용자 홈·임시 폴더 앞부분은 `%TEMP%\…`·`~/…` 로 바꾼다** — 최종 보고 「확인할 것」 표의 화면 행이 이 줄에서 경로를 옮긴다. 커밋 본문에는 이름만 둔다. 절대경로에는 사용자 이름이 들고, `plan.md` 를 추적하는 레포는 Progress Log 도 커밋·push 된다(`report-format.md`「plan 파일 커밋」).

### 완료 리뷰 대조

> `completion-reviewer` 가 `**화면**` 줄이 있는 task 를 볼 때 읽는다. 그 줄이 있는 task 에서만 쓰이는 대조라 리뷰어 정의가 아니라 화면 판정 줄 서식의 정본 곁에 둔다.

- **`**화면**` 줄이 있는 task 는 그 task 커밋 본문의 `화면:` 판정 줄이나 일괄 커밋의 `화면: T<N> …` 지목 줄(HEAD 판정·스크린샷 이름·시나리오·통과 조건)이 있는지 보고, 없거나 시나리오·통과 조건 칸이 비면 지적한다. 판정 없이 확인함으로 적혔으면 BLOCKER 다 — 검증 스킬이 없을 때의 `화면: 미촬영(HUMAN-VERIFY)` 줄은 정상이다. 미촬영이 아닌데 그 스크린샷의 Progress Log `화면 경로:` 줄이 없어도 지적한다** — 돌리지 않은 시나리오가 통과로 남고, 보고 「확인할 것」 표의 화면 행에 경로가 빈다.

- **전사 요약 경로를 받았으면 `화면: HEAD 참`·`화면: T<N> HEAD 참` 줄마다 그 스크린샷 이름이 대조 범위(`final-review.md`「전사 대조」)의 `T: Read <경로>` 줄에 있는지 본다 — 없으면 증거 누락 지적(`final-review.md`「절차」)이다. 그 판정 줄을 담은 커밋의 명령(`T: Bash git commit` 이 든 줄 중 제목이 그 커밋 제목인 것)이 대조 범위에 없으면 지적하지 않고 `전사 범위 밖 — 대조 불가 T<N>` 으로 적는다** — 스킬이 「성공」 을 내면 이미지는 열지 않고 참으로 적을 수 있는데, 위 「화면 시나리오 실행」 의 스크린샷 Read 대조를 지켰는지 남는 흔적은 전사의 Read 줄뿐이다. 앞 세션에서 커밋한 task 는 이 세션 전사에 없다.

- **검증 스킬이 있는 레포만 — 통과 조건이 `기준선 일치` 인 task 는 Progress Log `기준선: <이름> — HEAD <sha7>` 줄이 있는지, 그 sha 가 그 task 첫 커밋의 부모인지(`git rev-parse <첫 커밋>^`) 본다 — 줄이 없거나 sha 가 다르면 증거 누락 지적이다** — 편집 뒤에 찍은 기준선도 diff 0 으로 참이 되어 판정만으로는 갈리지 않는다. 스킬 없는 레포의 `기준선 일치` 는 미촬영 줄(BASE sha7·비교법 사유)이 정상이다.

## 최종 HEAD 재실행

> 4번 검증(`../SKILL.md`「검증」)의 한 부분이다 — plan 에 `**화면**` 줄이 있는 회차에서만 돈다. task 의 화면 판정은 그 task 커밋 시점의 HEAD 를 잰 것이라, 뒤 task·리뷰 수정·주석 정리가 같은 화면을 바꾸면 최종 HEAD 는 아무도 재지 않는다.

- **대상은 `**화면**` 줄이 있고 커밋 판정이 `참` 인 task 중, 그 task 의 마지막 `T<N>` 커밋 뒤에 코드가 바뀐 것이다 — `git diff --name-only <그 커밋>..HEAD` 에서 문서·이미지·`plan.md` 경로와, 바꾼 파일이 전부 그 레포 Release 의 버전 파일 집합인 커밋(`push-flow.md`「push 전 확인」 과 같은 판정)이 바꾼 경로를 빼고 하나라도 남으면 대상이다** — 화면마다 영향을 기계로 가를 수단이 없어 「그 task 뒤의 코드 변경」 으로 근사한다(사용자 답 「바뀐 화면만 재실행」 2026-11-14). 뒤에 바뀐 코드가 없는 화면은 task 판정이 곧 최종 HEAD 판정이다.
- **대상마다 같은 시나리오·통과 조건을 최종 HEAD 에서 위 「화면 시나리오 실행」 대로 돌리고 스크린샷 이름은 `final-<이름>` 이다 — 판정은 같은 둘(참·거짓)이고 스크린샷을 Read 로 열어 대조한다. `기준선 일치` 는 `final-<이름>` 을 그 task 의 `base-<이름>` 과 같은 `image-diff.ps1` 로 비교한다** — 검증 스킬이 없는 레포(미촬영 판정)는 대상이 아니다.
- **task 마다 Progress Log 에 `화면 재실행: <이름> — HEAD <sha7> <참 | 거짓 | 생략(<커밋 sha7> 뒤 코드 변경 없음)>` 한 줄을, 찍은 것은 `화면 경로: final-<이름> — <경로>` 도 남긴다** — 생략도 판정이라 줄을 남겨야 재지 않은 화면과 갈린다.
- **거짓이면 4번 실패다 — 고친 코드 커밋은 `final-review.md`「완료 순서」 의 4번 수정 커밋 경로이고, 고친 뒤 4번을 다시 돌 때 이 재실행도 다시 판정한다.**

## 확인할 것 — 화면 행

**사용자에게 스크린샷을 보이는 모든 보고 — 이 스킬·디버깅의 최종 보고와 체인 보고 — 는 스크린샷을 `report-format.md`「보고 형식」 의 「확인할 것」 표에 행으로 싣는다.** 자리마다 서식이 다르면 어떤 자리는 이름만, 어떤 자리는 「확인하라」 만 남는다. **push 는 이 표를 기다리지 않는다** — 열어 보는 것은 사용자의 선택이다(사용자 답 「바로 push + 스크린샷 보고」 2026-11-14).

| # | 무엇이 바뀌었나 | 수정 전 | 수정 후 |
|---|---|---|---|
| 1 | <화면 이름 — 통과 조건 한 구> | <base-<이름> 절대경로 · 없음(신규 화면) · 미확보 — <이유>> | <<이름> 절대경로> |
| 2 | 최종 재실행 <이름> | <그 task 의 <이름> 절대경로> | <final-<이름> 절대경로> |
| 3 | 기각 변형 <이름> | — | <절대경로> |
| 4 | 변경 검증 <기능> · <진입 경로> | <base- 가 있으면 그 경로 · 없으면 없음(BASE 화면 미촬영)> | <절대경로> |
| 5 | 기준선 차이 <이름> | — | <diff-<이름> 절대경로> |
| 6 | 기준선 흔들림 <이름> | <base2-<이름> 절대경로> | <diff-base2-<이름> 절대경로> |

- **`base-<이름>`(수정 전)과 `<이름>`(수정 후)은 한 행의 두 칸이다 — 다른 행으로 나누지 않는다** — 짝이 갈라지면 사용자가 어느 둘을 비교할지 맞춰야 한다(사용자 요구 「수정 전, 수정 후 같이 표시」 2026-11-17). 코디네이터 판정이 있는 화면 갈림길은 그 행의 「무엇이 바뀌었나」 칸 끝에 `(판정: <원문 한 구>)` 로 붙인다.
- **행은 이름에서 출발한다 — plan `**화면**` 줄(plan 없는 디버깅은 `../../karina-systematic-debugging/references/investigation-log.md`「화면 증거 (UI 재현)」 의 짝 — `base-` 는 그 수정 전 화면이다)의 이름마다 한 행이고, 기각 변형과 `**화면**` 줄 없이 검증 스킬 「변경 검증」 절로 조작한 화면도 한 행씩이다** — 경로 칸에서 출발하면 찍히지 않은 스크린샷이 행째 빠져 「확인하라」 만 남는다.
- **경로는 그 자리가 받은 출처에서만 온다 — Progress Log `화면 경로:` 줄 · 디버깅 조사 로그의 짝 · 체인 워커 `--body` 의 `확인할 것:` 칸. `%TEMP%\…`·`~/…` 표기는 절대경로로 펼치고, 싣기 전에 모든 경로의 실재를 한 번의 셸 호출(`ls -d <경로…>` · `Test-Path`)로 잰다** — 증거 폴더를 뒤져 짐작한 경로는 다른 실행의 스크린샷일 수 있고, 증거는 기한이 지나면 지워진다(`../../TEMP-FILES.md`).
- **경로가 없는 이름은 행을 지우지 않고 그 칸에 `없음 — <사유>` 로 적는다 — 미촬영이면 `미촬영(HUMAN-VERIFY): 시나리오 <…> · 통과 조건 <…>`(`**화면**` 줄에서), 파일이 사라졌으면 `파일 없음(<경로>) — 증거 기한 정리일 수 있다 · 시나리오를 다시 돌리면 다시 찍는다`, 출처에 칸이 없으면 `경로 미수신 — <어느 출처에 없었나>`** — 사용자가 무엇을 볼 수 없는지와 대신 무엇을 하면 되는지가 그 칸에 있어야 한다.
- **표는 로컬 보고에만 싣는다 — 커밋 메시지에는 싣지 않는다** — 절대경로에 사용자 이름이 든다.

# 루프의 호출 묶기

> `karina:implement` 가 루프 진입 전 1회 읽는다(`../SKILL.md`「진행 중 사용자와의 소통」). 루프가 도구를 언제·어떻게 부르는가를 정한다 — 정지 판정은 `loop-stop-patterns.md`, 실패 처리는 `loop-exceptions.md` 다.

## 호출 묶기

- **서로 입력이 되지 않는 호출은 한 메시지에서 함께 부른다 — task 준비의 plan 항목·Files Read·grep 과, 서로 의존하지 않는 검증 명령이 대상이다** — 메시지 하나가 모델 왕복 하나이고, 하니스 세션에서 왕복 1회가 약 30초였다(2026-11-15 9f29de47 — 99왕복 2982초). 순차로 부른 읽기 호출이 세션당 최대 56쌍 있었다(4cad6603).
- **앞 호출의 출력을 보고 다음 호출을 정해야 하면 묶지 않는다** — 묶으면 앞 출력이 정할 인자를 짐작으로 채운다.
- **검증 명령을 한 셸 호출로 이으면 명령마다 종료 코드를 남기고, 앞 명령이 실패해도 뒤 명령을 돌린다(`a; echo "a exit=$?"; b; echo "b exit=$?"`)** — `&&` 로 이으면 첫 실패에서 뒤 검사가 돌지 않아 실패가 하나만 보이고, 종료 코드 없이 출력만 이으면 어느 명령이 실패했는지 갈리지 않는다.
- **체크박스 `[x]` Edit 와 완료 커밋은 묶지 않는다** — 커밋 hook 이 Edit 결과를 읽어야 한다(`loop-exceptions.md`「실패 처리」).

## 검증 대기

- **task 검증 중 골든 러너(전체·부분)와 이 회차에서 직전 실측이 60초 이상이었던 명령은 백그라운드로 돌린다** — 포그라운드로 기다리면 그동안 루프가 아무것도 하지 못한다(2026-11-14 4cad6603 — 골든 부분 실행 16회 1482초). 수 초 안에 끝나는 검사는 대상이 아니다 — 띄우고 알림을 받는 왕복이 기다리는 시간보다 길다.
- **화면 검증 에이전트 요청(`screen-scenarios.md`「화면 시나리오 실행」)도 응답이 올 때까지 같은 대기다 — 에이전트가 앱을 빌드·조작하는 중이라 이 레포 편집은 `warn-screen-busy` hook 이 경고한다** — 2026-11-26 Karina 1518c748 이 검증 중 소스·`plan.md` 를 고쳐 판정이 더러운 트리를 빌드했고 두 변경이 한 커밋에 섞였다.
- **기다리는 동안에는 다음 task 를 읽기만 한다 — 그 task 의 plan 항목·`**함정**` 줄·Files 를 Read·grep 한다** — Edit·Write·커밋·체크박스·Progress Log 판정 줄은 쓰지 않는다. 검증이 실패하면 지금 task 를 고쳐야 하는데, 그 사이 다음 task 를 편집했으면 두 변경이 한 커밋 단위로 엉키고 판정이 실패한 변경 위에 선다.
- **통과 알림이 오면 지금 task 의 체크박스·완료 커밋을 끝낸 뒤 다음 task 편집으로 간다** — 커밋 전에 다음 task 를 고치면 두 변경이 한 커밋으로 엉킨다.
- **실패 알림이 오면 지금 task 로 돌아가 고치고(`loop-exceptions.md`「실패 처리」), 그 수정이 다음 task 의 Files 를 건드렸으면 그 파일을 다시 읽는다** — 먼저 읽은 내용은 수정 전 판이다.
- **읽을 것이 다하면 turn 을 끝내고 완료 알림을 기다린다 — 이 turn 종료는 정지 위반이 아니다(`loop-stop-patterns.md` 판정 단서)** — `loop-continue` hook 도 돌고 있는 백그라운드 작업이 있으면 turn 종료를 대기로 본다(`../../../scripts/rules/loop-continue-rationale.md`). 알림을 기다리며 결과 파일을 되풀이해 읽지 않는다.

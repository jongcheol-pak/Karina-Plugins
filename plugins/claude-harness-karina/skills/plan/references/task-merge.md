# 이웃 task 합치기

> `../SKILL.md`「Step 4. 작업 분해」 에서 이웃한 두 task 의 Files 가 겹치거나 같은 화면을 볼 때 읽는다. 체인 실측(`../../chain-plan/references/measure.md`)은 이 절을 인용해 task 초안에 쓴다.

## 합치기

- **이웃 task 둘의 Files 가 겹치거나 같은 화면을 보고, 같은 검증 명령으로 판정되며, 앞 task 결과만 따로 재야 할 이유가 없으면 한 task 로 합친다 — 합친 task 도 「한 번에 검증 가능한 크기」 여야 한다** — task 마다 빌드·기준선 촬영·화면 검증이 한 번씩 돌아, 따로 재서 얻는 판정이 없는 분할은 같은 검증을 두 번 치른다(2026-11-24 Karina plan 5 — 원 계획 이웃 16쌍 중 13쌍이 Files 가 겹친 채 따로 검증했다 · 사용자 관측 「합쳐서 작업해도 되는 내용을 너무 분할」).
- **「따로 재야 할 이유」 는 셋이다 — 앞 task 가 실패하면 뒤 task 를 시작하지 않아야 한다 · 두 동작의 실패를 한 검증 출력으로 가를 수 없다 · 사용자가 둘을 따로 되돌릴 수 있어야 한다** — 하나라도 참이면 합치지 않는다. 합친 task 가 실패했을 때 어느 변경 탓인지 가르지 못하면 합친 이득보다 재작업이 크다.
- **아래 자리는 합치지 않는다** — 각 규칙이 분할 자체를 판정 수단으로 쓴다.
  - 변경을 쉽게 만드는 prefactor 와 그 뒤의 동작 task(`../SKILL.md`「Step 4. 작업 분해」)
  - expand → 호출부 묶음 이전 → contract 의 각 단계(같은 절)
  - 구조만 바꾸는 task 와 동작을 바꾸는 task(`plan-template.md`「작업 단계」 — 구조 task 의 감소 계수·되돌림 단위)
  - 병렬 그룹 후보(`parallel-groups.md`「병렬 그룹」) — 동시에 돌 수 있는 독립 task 는 합치지 않고 그룹으로 묶는다
  - 검증 명령이 서로 다르거나 한쪽에만 성능 줄이 있는 task
- **합친 task 의 줄은 둘의 합집합이다 — Files·Acceptance 는 전부 싣고, 화면 줄은 한 시나리오 안에 두 동작을 지나게 적어 통과 조건을 이어 적는다. 검증 스킬 레포의 기준선 촬영은 그 task 첫 하위 항목 한 번이다** — 시나리오를 둘로 두면 합친 뒤에도 앱 기동·촬영이 두 번 돌아 줄이려던 비용이 남는다. task 마다 화면을 검증하는 규칙(`../../implement/references/screen-scenarios.md`「화면 시나리오 실행」)은 그대로다.

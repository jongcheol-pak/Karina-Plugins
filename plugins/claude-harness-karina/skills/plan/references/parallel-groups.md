# 병렬 그룹 (`karina:plan` Step 4 · `karina:implement` 진입 재확인)

> `../SKILL.md` Step 4 가 task 를 나눈 뒤 이 파일을 연다. 실행 쪽(`karina:implement`)도 그룹 진입 때 이 파일의 조건을 다시 잰다. 그룹이 없는 계획은 이 파일을 쓰지 않는다.

## 병렬 그룹

- **서로 독립인 이웃 task 2~3개만 묶는다 — 아래 넷 중 하나라도 거짓이거나 확신이 없으면 묶지 않는다** — 묶은 task 는 실행 쪽이 각자 worktree 서브에이전트로 동시에 돌리고, 메인이 task 번호 순으로 병합한 뒤 합친 트리에서 다시 검증한다. 조건이 틀린 그룹은 병합 충돌·통합 검증 실패로 순차 전환되어 오히려 느려진다.
  - ① **의존이 없다** — 뒤 task 가 앞 task 의 산출물(새 파일·심볼·문서 링크·커밋 sha·Progress Log 줄)을 전제하지 않는다. 그룹 바로 앞 task 들의 커밋만 전제할 수 있다
  - ② **Files 백틱 경로가 겹치지 않는다** — 케이스 파일·README·버전 파일·대장처럼 여러 task 가 함께 고치기 쉬운 공용 파일도 센다
  - ③ **새 체크아웃에서 검증이 돈다** — `git status --ignored --short` 에 그 task 검증 명령이 읽는 경로(`.env`·로컬 설정·빌드 캐시)가 있으면 묶지 않는다. `plan.md` 는 실행 쪽이 사본을 두므로 세지 않는다. 콜드 빌드가 task 하나보다 오래 걸리는 레포도 묶지 않는다
  - ④ **화면·성능·레포 밖 task 가 아니다** — `**화면**` 줄 task 는 상주 화면 검증 에이전트 하나가 앱 하나를 조작하고, `**성능**` 줄 task 는 동시 부하가 BASE 교대 측정을 오염시키며, Files 가 레포 밖이면 worktree 가 그 파일을 격리하지 못한다
- **크기는 2~3, 번호는 이웃해야 한다** — 동시 상한이 3이고(사용자 답 2026-11-21), 이웃만 묶어야 그룹 앞뒤 순서가 plan 순서와 같다. 넷 이상 독립이면 그룹을 나눈다.

## 서식

- **`## 작업 단계` 바로 아래, 첫 `### T` 앞에 한 줄로 쓴다** — `check-plan` 과 실행 쪽이 그 절의 첫 그룹 줄만 읽는다:

  ```
  > 병렬 그룹: T2·T3 | T5·T6·T7 — 근거: 의존 없음(<한 구>) · Files 겹침 없음 · 새 체크아웃 검증(<ignored 입력 요지>) · 화면·성능·레포 밖 없음
  ```

  - 그룹은 `|` 로, 그룹 안 task 는 `·` 로 가른다. 첫 ` — ` 뒤는 근거다.
  - 근거의 ③은 Investigation Log 의 `git status --ignored --short` 행으로 받친다.
  - 그룹이 없으면 줄을 쓰지 않는다 — 「없음」 줄도 두지 않는다. 승인 화면에는 `병렬: 없음 — <이유>` 로 보인다(`interview.md`「승인 제시」).

## 검사

- **크기·이웃·Files 겹침·④는 `../scripts/check-plan.ps1` 이 승인 전에 막고(코드는 그 머리 표 `parallel-*`), ①·③은 `plan-reviewer` 가 본다** — 의존과 ignored 입력은 문자열로 갈리지 않는다.

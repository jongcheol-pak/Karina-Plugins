# 조사 로그 서식

> `karina-systematic-debugging`의 조사 결과를 남기는 형식이다. **진행 중 루트 `plan.md`(미완료 `[ ]`/`[/]` task 가 남은 것 — 끝난 plan 은 진행 중이 아니다)가 있으면 그 끝에 아래 `## Debug:` 절을 Edit 로 덧붙이고, 없으면 파일을 만들지 않고 최종 보고에 싣는다** — 별도 조사 파일도 만들지 않는다.
> **`plan.md` 를 Write 로 쓰지 않는다** — 승인된 계획을 덮는다. 덧붙이는 절에는 task 체크박스를 넣지 않는다 — 실행 스킬이 task 로 읽는다.
> **조사를 시작할 때 이 서식을 열어 그대로 채운다** — 빈 칸이 곧 아직 안 한 일이다.
>
> 목차: 직접 재현 (1-B) / 피드백 루프 유형 (1-B) / 자동 신호가 없는 재현 (1-B · 4-A) / 화면 증거 (UI 재현) / 덤프·프로파일·트레이스 판독 (1-A) / 가설 작성 예 / Phase 1-D 경계 로깅 예 (WinUI 3 — "데이터가 화면에 안 보임") / 경량 경로를 썼을 때 / 분량 / 최근 변경 검사 명령 (1-C)

```markdown
## Debug: <증상 요약>

### Symptom
<무엇이 어떻게 잘못되는가>

### Reproduction
<재현 절차 — 다른 사람이 따라할 수 있게>

### Phase 1 — Evidence
- Error: <메시지 핵심 단서>
- Stack: <핵심 프레임>
- Recent changes: <git log 요약>
- Failing layer: <어디서 실패>

### Phase 2 — Hypotheses
- H1: <가설> — 예측: <무엇을 바꾸면 증상이 사라지나/악화되나> — 검증: <어떻게> → 결과: ✅/❌/⚠️
- H2: ...

### Phase 3 — Root Cause
<왜 그것이 원인인지 메커니즘 설명>

### Phase 4 — Fix
- Test added: <테스트 파일:케이스>
- Change: <파일:라인 + 한 줄 요약>

### Verification
- Build: OK
- RED: <명령> → <실패 판정 줄 원문 — 잘라 낸 자리는 …(N줄 생략)>
- GREEN: <명령> → <통과 판정 줄 원문>
- Original repro (같은 환경 재실행): <재현 절차 → 결과 판정 줄 원문 | 미검증 — <사유>>
- Screens: <base-<이름> — <경로> → <이름> — <경로> | 해당 없음 — 화면 없는 재현 | 미촬영(HUMAN-VERIFY) — <사유>>
- Commits: <재현 테스트 sha> → <수정 sha> | <sha>(한 커밋 — <사유>) | 없음 — <사유>
- PR: <URL | 건너뜀 — <사유>> · 수정 브랜치 <karina/fix-… | 지금 브랜치 그대로>
```

## 직접 재현 (1-B)

- **`AGENTS.md` 의 `Verify (앱 조작)` 줄이 검증 스킬을 가리키면 그 스킬의 기능 파일을 따라 앱을 조작해 재현한다. 사용자에게 재현을 맡기는 것은 검증 스킬·셸·테스트가 그 대상에 닿지 않는 구체적 이유를 대고 닿는 데까지 직접 간 뒤뿐이다** — 맡기면 그 이유와 멈춘 지점을 보고에 적고, 재현이 앱 조작인데 그 줄이 없거나 「없음」이면 사용자에게 `/karina:create-verification-skill` 을 한 구로 권한다.
- **`karina:implement` 루프 안이면 맡기지 않고 그 항목을 `HUMAN-VERIFY` 로 표기한 채 계속 간다.**

## 피드백 루프 유형 (1-B)

강한 것부터 고른다 — 이 신호가 그대로 Phase 4-A 의 회귀 테스트가 된다(근거 `debugging-rationale.md` §3).

| 유형 | 쓰는 자리 |
|---|---|
| **실패하는 단위 테스트** | 가장 강함. 버그를 재현하는 최소 케이스 |
| **격리 재현 스크립트** | 앱 전체 없이 문제 경로만 실행해 결과를 단정 |
| **반복·타이밍 재현 루프** | 산발·동시성 버그를 N회 반복해 빈도를 신호로 |
| **`git bisect` 하네스** | 회귀의 도입 커밋을 자동으로 좁힌다(1-C와 결합) |
| **로그-grep 단언** | 테스트가 어려운 경우, 특정 로그 라인 유무를 pass/fail로 |

## 자동 신호가 없는 재현 (1-B · 4-A)

위 표의 신호를 만들 수 없을 때(UI·환경 의존) 수동 재현이 증거가 되려면 넷을 갖춘다.

- **정상 최종 상태와 깨진 최종 상태를 먼저 이름 붙인다 — 중간의 로딩·예상된 대화상자·설정 단계는 버그가 아니다** — 무엇이 깨진 상태인지 정하지 않으면 재현이 성공했는지 갈리지 않는다.
- **상태를 리셋해 서로 독립인 재현을 2회 한다** — 한 번의 관측은 이전 시도가 남긴 상태가 만든 것일 수 있다.
- **읽기 전용 상태 조회로 관측을 교차 확인하되, 내부 setter·저장소 직접 쓰기로 증상을 만들지 않는다** — 주입한 증상은 원래 경로가 그 상태에 이르는지를 증명하지 못한다.
- **그 환경이 없으면 결함을 플랫폼 명사 없이 다시 서술해 쓸 수 있는 환경에서 같은 동작을 시험하고 `번역된 증거` 로 표시한다 — 빠진 환경이 결함의 일부면 정확한 재현이라 부르지 않는다** — 곧바로 「재현 불가」로 멈추면 시험할 수 있던 동작까지 버리고, 번역한 결과를 정확한 재현이라 부르면 환경 차이가 원인인 경우를 놓친다.

## 화면 증거 (UI 재현)

1-B 재현이 앱 화면 조작일 때(검증 스킬이든 수동이든) 수정 전후의 같은 화면을 스크린샷 짝으로 남긴다. 단위 테스트·CLI·로그로 재현한 버그는 대상이 아니다 — 판정 줄 원문이 이미 증거다. `karina:implement` 루프 안이면 대상이 아니다 — 그 task 의 `**화면**` 줄이 맡는다. Cursor pstack benny 의 reproduce-and-fix-issues 를 들였다(`https://github.com/cursor/plugins/blob/c742dd61706fbacc1b95f1a20b7b988cf096ce6c/pstack/automations/benny/skills/reproduce-and-fix-issues/SKILL.md` — *"Only after before-and-after proof:"*).

- **수정 전 — 1-B 재현의 깨진 최종 상태를 `AGENTS.md` `Verify (앱 조작)` 검증 스킬의 Evidence 로 `base-<이름>.png` 에 남긴다. `<이름>` 은 증상을 가리키는 영문 kebab-case 다** — 수정한 뒤에는 깨진 화면을 다시 얻을 수 없다.
- **수정 후 — 4-D 재실행에서 같은 시나리오의 끝 상태를 `<이름>.png` 에 남긴다. 판정은 수정 전 거짓·수정 후 참일 때만 통과다(판정 표 `../../implement/references/report-format.md`「화면 시나리오 실행」)** — 수정 전에도 참인 화면은 이 수정을 재지 않는다. 이름을 그 절과 맞춰야 `pr-verifier` 와 ship 화면 게이트가 디버깅 PR 에서도 읽는다.
- **짝 중 하나라도 없으면 4-D 를 통과로 적지 않고 `미검증 — 스크린샷 짝 없음(<사유>)` 으로 적는다. 검증 스킬이 없어 수동으로 재현했으면 `미촬영(HUMAN-VERIFY)` 으로 적고 시나리오·이름·통과 조건을 남긴다** — 판정 줄만으로는 사용자가 화면이 실제로 고쳐졌는지 볼 수 없고, 시나리오가 남아야 사용자가 같은 것을 돌린다.
- **두 경로를 최종 보고 「확인할 파일」 에 싣고, 커밋·PR 에 싣는 자리는 `../../implement/references/pr-flow.md`「디버깅 단독 경로」 다** — 사용자가 열어 볼 자리가 보고이고, merge 를 막는 자리가 PR 이다.

## 덤프·프로파일·트레이스 판독 (1-A)

크래시 덤프·프로파일·힙 스냅샷·트레이스처럼 이미 캡처된 아티팩트가 증거일 때 읽는 법이다. Cursor pstack 의 trace-forensics 를 들였다(`https://github.com/cursor/plugins/blob/8b3326d99fd4b993cb33a24dad8af03175c642c5/pstack/skills/poteto-mode/playbooks/trace-forensics.md`).

- **캡처는 고정된 데이터다 — 다시 돌리지 않고 읽는다** — 같은 조건이 다시 나온다는 보장이 없고, 다시 돌린 결과는 다른 캡처다.
- **큰 캡처는 쿼리할 수 있는 형태(표·sqlite·도구의 요약 출력)로 바꾼 뒤 읽는다** — 원본을 훑으면 시간이 가장 많이 든 프레임이나 객체를 붙잡는 유지 경로를 순서 없이 본다.
- **소스 매핑(심볼·파일·줄)이 없는 프레임은 아직 진단이 아니다 — 심볼을 해결하거나, 캡처에 심볼이 없다고 밝힌다** — 주소나 모듈 이름만으로 원인을 적으면 그 위치를 코드에서 확인할 수 없다.
- **같은 조건의 전후 짝 캡처가 있으면 diff 로 확인하고, 없으면 결론을 「캡처가 지지하는 가장 강한 가설」로 적는다** — 단일 캡처는 그 시점의 상태를 보일 뿐, 그것이 원인인지는 Phase 3 의 검증이 정한다.

## 가설 작성 예

**예측 필드가 가설을 반증 가능하게 만든다.** "무엇을 바꾸면 증상이 사라지거나 악화되는가"를 미리 못 적으면 그 가설은 아직 모호하다는 신호다 — 검증할 것이 없기 때문이다.

```
WRONG: H1: 캐시가 문제인 것 같다 — 검증: 캐시를 본다
RIGHT: H1: 만료된 캐시 항목을 stale로 반환한다 — 예측: TTL을 0으로 두면 증상이 사라진다 — 검증: TTL=0으로 재현 시도
```

## Phase 1-D 경계 로깅 예 (WinUI 3 — "데이터가 화면에 안 보임")

```csharp
// 레이어 1: API/Repository
_logger.LogInformation("[Repo] Fetched count={Count}", items.Count);
// 레이어 2: Application/Domain
_logger.LogInformation("[Domain] After filter count={Count}", filtered.Count);
// 레이어 3: ViewModel
_logger.LogInformation("[VM] Items.Count={Count}", Items.Count);
// 레이어 4: View binding — XAML 디버깅 출력 또는 Live Visual Tree
```

이러면 **어느 레이어가 실패하는지** 드러난다(예: Repo ✓ → Domain ✓ → VM ✗ → 바인딩 문제).

## 경량 경로를 썼을 때

**보고에 「경량 경로」를 명시하고 어떤 단계를 왜 생략했는지 적는다.** 위 서식에서 `### Phase 2 — Hypotheses`·`### Phase 3`을 비우는 대신 한 줄로 대체한다:

```markdown
### 경량 경로
- 근거: <컴파일러/스택트레이스가 짚은 파일:라인:원인>
- 생략: Phase 1-B~1-D · 2 · 3 (원인이 이미 확정)
```

## 분량

- **각 절은 다음 Phase 판정에 쓰이는 것만 담는다** — 증상 배경·코드 동작 설명은 원인 확정에 기여하지 않으면서 이미 모은 단서를 그 아래 묻는다(출처: Opus 5 가이드 「작성된 산출물의 길이」).
- **기각된 가설은 지우지 말고 `❌` + 한 구 사유만 남긴다** — 지우면 다음 세션이 같은 가설을 다시 세우고, 서술을 통째로 남기면 확정된 원인이 그 사이에 묻힌다.

## 최근 변경 검사 명령 (1-C)

```bash
git log -n 20                                 # 최근 20개 — 본문 포함
git diff --stat HEAD~N..HEAD -- <의심 파일>   # 규모를 먼저 잰 뒤 큰 파일만 전문으로
git diff HEAD~N..HEAD -- <의심 파일>
git log -n 20 --since="N hours ago"           # 개수 상한을 함께 — 본문은 유지한다
git blame -L <시작>,<끝> <파일>               # 범위를 모르면 -L 없이 쓰되 파일을 좁힌다
git log -S'<코드의 리터럴>' -n 20 -- <파일>     # 그 리터럴이 들어오고 나간 커밋 — 20개 밖의 도입도 찾는다
git log --follow -n 20 -- <파일>              # 이름이 바뀐 파일의 이전 이력까지
git log -i --grep=revert -n 10 -- <파일>      # 되돌린 수정 — 다음 시도가 앞 실패에서 시작하게
```

> **`git log` 본문은 유지한다**(`--oneline` 금지) — 커밋 본문이 단서다. 근거는 `debugging-rationale.md` §10.

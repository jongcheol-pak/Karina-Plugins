Copyright (c) 2026 Lauren Tan · MIT(`https://github.com/cursor/plugins/blob/ae5650febf4320793844c12c4adaa937f417f8da/pstack/LICENSE`). 한글로 옮기며 원문과 다르게 한 것 — ① 대상 찾기를 `AGENTS.md` 의 `Verify (형식 검증)` 줄과 그 스킬의 「변경 검증」 절로, 줄이 없으면 하는 일 대신 생성 스킬이 붙이는 `formal-*` 이름으로(무관한 스킬을 유지 대상으로 오인하지 않게) ② 덮는 코드·동기 커밋이 없는 기존 스킬의 폴백 ③ 도구가 없으면 설치하지 않고 blocked ④ 5단계에서 bug 반례를 알려진 위반에 올리고 감시 경로를 갱신함(올리지 않으면 `gate-verifier` 가 그 반례를 새 위반으로 쳐 감시 경로에 걸리는 모든 push 전 게이트가 실패한다) ⑤ 산출을 `../maintain-verification-skill/SKILL.md`「진행」 6번의 커밋·push 경로로 ⑥ 버그 수정을 `karina:plan`·`karina:karina-systematic-debugging` 으로 넘김. 덧붙인 것 — 조건 앵커와 반례 재현 증거 기준을 — 앵커는 create-formal 원문(`https://github.com/cursor/plugins/blob/ae5650febf4320793844c12c4adaa937f417f8da/pstack/skills/create-formal-verification-skill/SKILL.md`) 「코드에 충실하다」 의 *"Every part of the model or proof points to code that a reviewer can open."* 를 `파일:줄` 로 구체화한 karina 규칙이고(처음 출처였던 statechart 스킬의 앵커 문면은 최신본에 없다), 증거 기준은 statechart 의 *"replay each bug path against the real code"*(`https://github.com/cursor/plugins/blob/ae5650febf4320793844c12c4adaa937f417f8da/pstack/skills/statechart/SKILL.md`)와 principle-test-behavior-not-implementation 의 관측 가능한 동작 축(`https://github.com/cursor/plugins/blob/ae5650febf4320793844c12c4adaa937f417f8da/pstack/skills/principle-test-behavior-not-implementation/SKILL.md`)이다 — 3·4단계에.

형식 검사는 자기가 서술하는 것의 속성을 증명한다. 코드가 바뀌었는데 검증이 그대로면, 검사는 더는 없는 코드를 서술한 채 계속 통과할 수 있다. 그 통과가 위험한 경우다 — 증명처럼 보이기 때문이다. 이 스킬은 `/karina:create-formal-verification-skill` 이 만든 검증 스킬(또는 모델 체커·증명기·코드 검증기를 이름 댄 코드에 돌리는 다른 프로젝트 스킬)의 유지 루프다. 프로젝트 스킬은 에이전트가 그 스킬을 쓰며 만든 변경을 다룬다. 이 스킬은 그것을 건너뛴 변경을 다룬다 — merge, 스킬 없이 한 편집, 여러 커밋에 걸쳐 쌓인 드리프트.

## 결과

검사마다 하나를 고르고, 어느 것인지 말한다.

- **in sync** — 마지막 동기 이후 검사가 서술하는 것을 바꾼 변경이 없고, 검사가 통과한다.
- **updated** — 코드가 바뀌었고, 검증이 이제 새 코드를 서술하며, 검사가 통과한다.
- **bug** — 검증이 지금 코드를 서술하는데, 코드가 속성을 깬다. 코드에 대한 발견이지 드리프트가 아니다.
- **blocked** — 검사를 코드에 다시 맞추지 못했거나 돌리지 못했다. 정확히 왜인지 말한다.

한 검사가 updated 이면서 bug 일 수 있다 — 갱신이 검증을 다시 코드를 서술하게 만들고, 그 위에서 속성이 실패한다.

## 편집 범위

**검증만 고친다** — 모델·하네스·속성 파일과 검증 스킬 자신. 실행 중에 제품 코드는 사용자가 요청하지 않으면 고치지 않는다(수정은 `karina:plan`·`karina:karina-systematic-debugging` 의 일이다). 지금 코드에서 속성이 실패하면 통과하게 하려고 속성이나 모델을 약하게 바꾸지 않는다 — 실패를 보고한다.

## 진행

0. **대상을 찾는다** — 사용자가 하나를 지목했으면 그것만 본다. 아니면 `AGENTS.md` 의 `Verify (형식 검증)` 줄이 가리키는 스킬(보통 `.claude/skills/formal-*/`)이고, 지목이 없고 줄이 없거나 「없음」이면 `.claude/skills/formal-*/SKILL.md` 를 찾아 대상으로 삼고 보고에 「미등록 — `AGENTS.md` `Verify (형식 검증)` 줄 없음」 과 등록 경로(`../create-formal-verification-skill/SKILL.md`「6. 등록한다」)를 싣는다 — 본문 첫 줄이 `> 초안` 인 스킬은 대상에서 빼고 보고만 한다. 찾은 것도 없으면 대상을 지어내지 않고 멈춰 `/karina:create-formal-verification-skill` 을 안내한다. 스킬마다 본문에서 속성·한계·가정을, 「변경 검증」 절에서 감시 경로·검사 명령·알려진 위반·덮는 코드·동기 커밋을 모은다.
   - **동기 커밋이 없으면** 검증 파일을 마지막으로 바꾼 커밋(`git log -1 --format=%H -- .claude/skills/formal-<영역>`)을 쓰고, 그렇게 했다고 보고한다.
   - **덮는 코드가 없으면** 감시 경로 glob 과 모델·하네스가 이름으로 가리키는 심볼을 덮는 코드로 쓰고, 5단계에서 그 항목을 채운 뒤 그렇게 했다고 보고한다 — 두 항목이 생기기 전에 만든 스킬이 있다.
1. **그대로 돌린다** — 아무것도 바꾸기 전에 검사마다 한 번 돌리고 결과를 적는다. 여기서의 통과는 코드가 맞다는 뜻이 아니라 옛 서술이 아직 성립한다는 뜻이다. 여기서의 실패는 드리프트일 수도 버그일 수도 있다 — 4단계 전까지 가르지 않는다. **도구가 없으면 설치하지 않고** 그 검사를 blocked 로 두고 고른 설치 명령을 보고한다(설치는 `../create-formal-verification-skill/SKILL.md`「2. 질문이 도구를 고르게 한다」 대로 승인 뒤에만).
2. **덮는 코드의 변경을 전부 읽는다** — 동기 커밋부터 지금 커밋까지 덮는 파일을 diff 하고 커밋 메시지를 하나씩 읽는다. 옮겨진 코드도 본다 — 이름이 바뀌거나 쪼개지거나 다른 파일로 간 덮는 함수는 여전히 덮는 코드다. 검사가 지키는 상태를 건드리는 새 코드도 본다 — 같은 필드를 쓰는 새 함수 같은 것. 변경마다 넷 중 하나로 가른다.
   - **영향 없음** — 서식·주석·검증이 덮지 않는 경로처럼 검증이 서술하는 것을 바꾸지 않는다. 커밋 메시지가 아니라 모델·하네스에 대조해 판정한다.
   - **검증이 코드를 더는 서술하지 않는다** — 쪼갤 수 없던 한 단계가 둘이 됐거나, 분기가 생기거나 없어졌거나, 검사가 옮겨졌거나, 지키는 상태에 닿는 새 경로가 생겼거나, 값의 범위가 달라졌다. 모델이나 하네스가 바뀌어야 한다.
   - **약속이 의도적으로 바뀌었다** — 변경이 코드의 약속을 바꾸고, 변경 안의 증거(doc 주석·테스트·changelog·커밋 메시지)가 그것이 의도임을 말한다. 속성이 바뀌어야 하고, 그 증거를 인용해야 한다.
   - **약속이 깨졌을 수 있다** — 코드가 바뀌었는데 약속이 바뀌었다는 증거가 없다. 뒤따르는 실패를 버그 후보로 본다.
3. **결과가 아니라 코드에서 고친다** — 바뀐 부분마다 리뷰어가 열어 볼 수 있는 코드를 다시 가리키게 모델·하네스를 고치고, 코드의 쪼갤 수 없는 한 단계는 검증에서도 한 단계로 둔다. 다시 돌리기 전에 코드에서 쓰고, 검사가 통과하는 쪽으로 다듬지 않는다. 고치거나 더한 조건마다 그 조건을 검사하는 코드의 `파일:줄` 앵커를 새 위치로 갱신하고, 앵커가 없던 기존 조건에도 이번에 단다. 속성은 의도적으로 바뀐 약속에만 고친다 — 옛 문구·새 문구·증거를 적는다. 한계는 변경이 그것을 틀리게 하지 않는 한 유지하고, 줄여야 하면 보고에 적는다.
4. **다시 돌려 결과마다 판정한다**
   - **통과** — 검사가 이제 실패할 능력을 잃은 서술 위에서 통과할 수 있다. 속성이 막는 방식으로 새 코드를 일부러 깨뜨려(새 검사 하나를 지우거나 새 단계의 순서를 바꿔) 검사가 잡는지 확인한 뒤 그 깨뜨림을 되돌린다. 앵커 없는 조건이 남아 있으면 깨뜨림으로는 그 조건을 잡지 못하므로, 결과는 그대로 판정하고 앵커 없는 조건 목록을 보고에 싣는다.
   - **실패** — 반례를 실제 코드에서 한 단계씩 재생한다. 어느 단계가 코드에서 일어날 수 없으면 검증이 틀린 것이다 — 검증을 고치고 무엇이 틀렸는지 말한다. 재생에서 버그가 나면 버그다 — 단계가 모두 가능해 보여도 재생에서 버그가 나지 않으면 모델이 맞다는 것을 보이기 전까지 모델이 틀렸다고 본다. 버그면 도입한 커밋을 이름 대고, 반례를 코드의 말로 쓴 단계 순서로 말하고, 피해를 한 문장으로 적는다. 실제 코드에 대한 싼 테스트·재현이 버그를 보이면 증거로 보고에 넣되 제품 코드에 커밋하지 않는다 — 무엇이 증거가 되는가(진입점만 구동 · 스스로 세운 값은 단언하지 않음 · 실행 증명과 코드 읽기 증명을 나눔)는 `../create-formal-verification-skill/SKILL.md`「3. 좋은 검증의 조건」 의 「발견은 발견으로 남는다」 그대로다.
5. **검증 스킬을 갱신한다** — 검사마다 덮는 코드 · 감시 경로(이동·분할로 새로 덮게 된 파일 포함) · 알려진 위반(bug 로 판정한 반례 요지를 올린다 — `gate-verifier` 가 그 목록으로 새 위반을 가른다) · 검사 명령 · 한계 · 가정 · 동기 커밋을 고친다. 동기 커밋은 이번에 확인한 커밋으로 둔다. blocked 인 검사는 동기 커밋을 옮기지 않고 그렇게 보고한다. 그런 다음 다음 에이전트처럼 검증 스킬을 한 번 그대로 따라 단계가 아직 도는지 본다.
6. **내거나 멈춘다** — 검증 스킬 폴더에 변경이 하나라도 있으면(알려진 위반 추가도 변경이다) 고친 파일을 모두 다시 읽은 뒤 `../maintain-verification-skill/SKILL.md`「진행」 6번과 같은 경로로 낸다 — 커밋은 `git add -- .claude/skills/formal-<영역>` 뒤 `git commit -m "문서: 형식 검증 스킬 formal-<영역> 동기화" -- .claude/skills/formal-<영역>`(`git check-ignore -q --no-index …/SKILL.md` 가 0 이면 `git add -f --`)이고, 커밋 본문에 검사별 결과와 bug 반례를 적는다. 0번의 미등록 스킬이 `git check-ignore -q` 0(추적하지 않는 무시 경로)이면 커밋하지 않고 보고에 변경 경로만 싣는다 — 추적하지 않기로 한 것은 사용자 선택이다(`../create-formal-verification-skill/SKILL.md`「6. 등록한다」). 제품 수정은 넣지 않는다. 변경이 없으면 커밋도 없다.

실행 메모(읽은 커밋 · 변경 분류 · 쓴 깨뜨림 · 결과)는 레포 밖 임시 위치에 짧게 남기고 커밋하지 않는다.

## 보고

검사마다 — 결과와 읽은 커밋 · 검증에서 무엇을 왜 바꿨는가(코드의 모양이 바뀌었다 | 약속이 의도적으로 바뀌었다 — 증거) · 다시 돌린 결과와 갱신한 검사가 아직 실패할 수 있음을 보인 깨뜨림 · 버그마다 코드의 말로 쓴 반례·피해·도입 커밋 · 검증이 아직 덮지 않는 것(덮어야 하는데 안 덮는 새 코드 포함) · 앵커 없는 조건 목록(없으면 「없음」) · 커밋 sha 와 push 결과(또는 건너뛴 사유) · blocked 면 설치 명령 또는 막은 것.

어느 실패가 검증 드리프트이고 어느 것이 코드 버그인지 명시한다. 갱신 전에 통과하고 갱신 뒤에 실패한 검사는 옛 통과가 낡은 서술 위였다고 말한다. 문장은 `../WRITING.md` 를 따른다.

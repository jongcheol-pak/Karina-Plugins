# claude-harness-karina (자율 루프)

> Claude Code가 **계획하고 검증하며** 일하도록 만드는 plugin (Windows 우선 · pwsh 7 또는 내장 PowerShell)
> <br>(계획·검증 로직은 OS 무관 — 단 `chain-plan` 은 Karina 앱(Windows)가 필요하다, 자동 안전망 hook은 pwsh 7 우선·없으면 Windows 내장 PowerShell로 폴백 — Windows 검증·macOS/Linux 실험적, [호환 환경](#호환-환경) 참고)

**버전**: 2.31.0
**저장소**: https://github.com/jongcheol-pak/Karina-Plugins (모노레포 — 이 하니스는 plugins/claude-harness-karina/ 폴더)
**Claude Code**: 최소 v2.0 — 플러그인을 쓰는 데는 이것으로 충분하다. CLAUDE.md 가 없는 프로젝트에서 Claude Code 가 AGENTS.md 를 직접 불러오는 것은 v2.1.277+ 이고, 그 미만이면 세션 시작 hook 의 Read 지시가 대신한다 · **하니스 자체를 고칠 때(eval 러너)는 권장 v2.1.269+** — `--filter` 이름 검증과 골든 러너 병렬 모드가 안정된 판이라, 그 미만에서는 부분 실행 필터가 조용히 0건을 돌 수 있다. <!-- verified: 2026-09-12 -->

## 한눈에 보기

Claude Code에게 코딩을 맡기면 가끔 이렇게 합니다:

- 계획 없이 바로 코드를 쓰고, 있지도 않은 함수를 호출
- A 파일만 고치고 그걸 부르는 B·C 파일은 그대로 둬서 빌드가 깨짐
- 제대로 확인 안 하고 "다 됐습니다"라고 보고
- task마다 "다음 진행할까요?"를 물어 흐름이 끊김

**karina는 이걸 막습니다.** 코드를 바꾸기 전에 먼저 계획을 세우게 하고, 바꾼 뒤에는 여러 단계로 검증하게 하며, 한 번 승인하면 끝까지 자동으로 진행합니다. "꼼꼼한 시니어 개발자의 작업 습관"을 Claude Code에 입히는 도구라고 보면 됩니다.

비유하자면, Claude Code가 "재능 있지만 가끔 덤벙대는 주니어"라면, karina는 그 옆에서 "계획서 보여줘 → 이 부분 빠졌네 → 검증했어? → 좋아 통과"를 챙기는 **작업 절차와 안전장치**입니다.

> 특정 언어 전용이 아닙니다 — 빌드/테스트 명령만 알면 **어떤 언어·프로젝트에서도** 동작합니다. (.NET·Android·Node/TS·Python·Go·Rust는 표식 파일로 자동 감지해 빌드·테스트 명령까지 채우고, 그 외는 물어서 채웁니다)

## 무엇을 해결하나요

| 자주 겪는 문제 | karina의 대응 |
|---|---|
| 추측으로 코드를 쓰고, 없는 함수를 호출 | 코드 변경 전 영향 범위를 전부 조사하고, 계획을 적대적으로 검토 |
| A만 고치고 B·C를 빠뜨림 | 변경할 때마다 그걸 쓰는 다른 파일을 자동으로 찾아 함께 점검 |
| 확인 없이 "다 됐다"고 보고 | 빌드·테스트 + 2단계 검토 + 자기점검을 통과해야만 완료 |
| task마다 "다음 할까요?" 물음 | 한 번 승인하면 모든 task를 끝까지 자동 진행 |
| 사소한 오타 수정에도 거창한 절차 | 3줄 이내 단순 수정은 절차를 건너뛰고 바로 처리 |
| 빌드·테스트 명령을 매번 모름 | 프로젝트를 분석해 명령을 자동으로 파악·기록 |
| DB 데이터를 실수로 삭제·변조 | 위험한 DB 명령(전체 삭제/변조 등)을 자동 차단 |
| 과거에 한 작업을 매번 다시 조사 | 프로젝트 지식을 위키에 쌓고, 다음 작업 때 참조 |

## 빠른 시작

### 1. 사전 요구사항

- Windows 10/11 + PowerShell (내장 5.1 로 충분 · pwsh 7 이 있으면 그쪽을 우선 사용)
- macOS/Linux: pwsh 7 필요 — 동작하도록 구현했으나 실제 환경 미검증(실험적), `chain-plan` 은 Windows 전용 ([호환 환경](#호환-환경))
- Claude Code v2.0 이상

### 2. 설치

```powershell
claude plugin marketplace add jongcheol-pak/Karina-Plugins
claude plugin install karina@karina-plugins
claude plugin enable karina@karina-plugins
```

설치가 끝나면 Claude Code를 다시 시작합니다. 마켓 `karina-plugins` 는 여러 플러그인을 담고, 플러그인마다 `<플러그인>@karina-plugins` 로 따로 설치합니다.

### 3. 첫 사용

평소처럼 말하면 됩니다. karina가 알아서 끼어듭니다:

```
> 로그인 화면에 "비밀번호 찾기" 링크 추가해줘

[karina가 자동으로]
1. 계획을 세우고 → 검토한 뒤 → 당신에게 승인을 받습니다
2. 승인하면 → 구현하고 → 검증하고 → 완료를 보고합니다
```

처음 코드 작업을 시도하면, karina가 **작업에 필요한 명령·규칙**(빌드·테스트 명령, 인코딩 규약, 금지 항목)을 담은 `AGENTS.md` 파일을 만들자고 제안합니다. 처음에는 빌드·테스트 명령과 아키텍처 선언 1줄만 채우고, 나머지는 작업하며 확인되는 대로 채워집니다(추측해 채우지 않습니다).

> **`AGENTS.md`에는 프로젝트 정보를 넣지 않습니다.** 매 세션 전문이 로드되는 파일이라, 구조·진행 상태처럼 계속 쌓이는 내용을 담으면 그만큼 컨텍스트를 차지합니다. 프로젝트 성격·기술 스택·구조는 **위키가 정본**이고 `AGENTS.md`에는 위키로 가는 한 줄만 둡니다. 위키에 없는 프로젝트는 계획을 세울 때 자동으로 등록됩니다.

## 어떻게 동작하나요

karina는 코드 작업을 **계획 → 구현 → 검증 → 완료**의 흐름으로 진행합니다.

### 1단계 — 계획 (당신과 함께)

요청을 받으면 바로 코드를 쓰지 않고 먼저 계획을 세웁니다.

- **영향 범위를 전부 조사**하고, 새로 만들기 전에 이미 있는 코드·공통 컴포넌트를 먼저 찾아 재사용합니다.
- **함께 다룰 것을 계획 전에 한 번에 제안**합니다 — 같이 고쳐야 할 문서·검증 자산, 미뤄 둔 작업 대장과 겹치는 항목, 근거 있는 추가 기능(최대 3개)을 한 목록으로 보여 주고 포함/제외/보류를 받습니다. 작업이 끝난 뒤에야 "추가로 고칠 곳이 있습니다"라고 알리지 않기 위해서입니다.
- 모호한 부분은 **선택지로 묻습니다** — 당신이 이미 말한 방향은 반드시 선택지에 들어가고, 추천은 빨리 끝나는 안이 아니라 문제가 사라지는 안에 붙습니다. 서로 무관한 질문은 한 번에 최대 3개까지, 「yes」 한 마디로 권장안을 받을 수 있게 씁니다.
- **화면 결정은 보이는 모습으로 묻습니다** — 레이아웃 같은 질문에는 임시 변형 2~3개의 스크린샷을 선택지로 붙입니다. 실행해 보면 답이 나오는 것은 묻지 않고 실험으로 정합니다.
- 계획이 고른 설계에 결함(메모리 증가 등)이 있으면 결함 없는 설계를 기본으로 고르고, 그 설계가 다른 비용을 만들 때만 묻습니다.
- 계획에는 작업 단위(T1, T2, …)와 함께 **근거가 붙은 전제**, 새 파일을 두는 이유, 성능 작업이면 **수치 기준**(지표·측정법·현재값·실패 기준), 완료 판정 명령의 **현재 실행 결과**가 들어갑니다. 위키·`docs/conventions.md` 에 적힌 함정은 그것이 걸리는 task 옆에 붙습니다.
- 스크립트가 계획서 서식을 먼저 검사하고, 별도 **검토 담당**이 계획이 실측 위에 서 있는지(돌리지 않은 명령·빠진 호출자·판정할 수 없는 완료 조건·task 끼리의 충돌)를 봅니다. 지적을 고치면 다시 검토합니다(최대 3라운드). 따지기로 task 나 완료 조건이 바뀌면 한 번 더 검토합니다.
- 완성된 계획을 **`T1: …` 처럼 한 줄씩 요약해 보여 주고** 승인을 기다립니다 ✋ — **바로 구현** 대신 **새 세션에서 구현**을 고르면 새 세션에 붙여 넣을 `/karina:implement …` 한 줄을 줍니다. **따지기**를 고르면 모델이 묻지 않고 정한 결정과 가정을 하나씩 끝까지 묻고, 답대로 계획을 고친 뒤 다시 보여 줍니다.

> **승인은 한 번입니다.** 계획에 적힌 승인 필요 항목(비파괴 DB 스키마 변경 등)과 push·PR 생성·merge 는 이 승인에 포함돼 진행 중 다시 묻지 않습니다. 태그·릴리즈·배포, 계획에 없던 파괴적 작업, 되돌릴 수 없는 변경(환경변수·시크릿·DB 데이터·외부 호출)만 그 지점에서 따로 승인받습니다. git 으로 되돌릴 수 있는 변경은 멈추지 않고 진행한 뒤 완료 보고의 「판정」에 적고, 요청과 무관한 곁가지는 하지 않고 대장에 기록해 다음으로 넘깁니다.

### 2단계 — 구현 (자동)

승인하면 여기서부터는 **끝까지 자동**입니다. task마다 다음을 반복합니다:

1. 이 변경이 다른 곳에 영향을 주는지 미리 추적
2. 최소한으로 코드 수정 — 바꾸는 영역의 죽은 코드·고아 코드를 먼저 지우고, 주석은 꼭 필요한 것만 남깁니다(정본 `skills/implement/references/code-style.md`)
3. 빌드·테스트 + 검증
4. 통과하면 커밋하고 즉시 다음 task로

- 중간에 "다음 할까요?"라고 묻지 않고, 화면에는 **task 시작·완료 한 줄씩**만 나옵니다. 문제가 생겼을 때만 멈춥니다.
- 계획서에 승인 표지가 없으면 승인 전 초안일 수 있으니 실행 전에 한 번만 묻습니다.
- **GitHub 원격이 있고 `gh` 가 로그인돼 있으면** `karina/<작업 이름>` 브랜치에서 작업하고 끝에 push 해 PR 을 엽니다. 화면을 바꿨으면 PR 본문에 스크린샷 경로를 싣습니다. CI 대응과 merge 는 요청하면 `karina:pr` 이 맡습니다.

### 3단계 — 검증과 완료

모든 task가 끝나면 전체를 한 번 더 통합 검증하고, 빌드·테스트·검토를 모두 통과한 뒤에야 완료를 보고합니다.

- **완료 표시마다 증거를 대조합니다** — 완료로 체크된 task 마다 커밋과 검증 기록이 있는지 스크립트가 보고, 검토자가 판정 명령을 직접 다시 돌려 봅니다.
- **자기가 만든 문제는 「남은 이슈」로 넘기지 않습니다** — 이번 변경 때문에 깨진 것은 같은 작업 안에서 고칩니다. 남은 이슈에는 원래 있던 별개 문제·범위 밖으로 정한 것·개선 제안만 올라갑니다.
- **화면 확인은 검증 스킬로 먼저 해 봅니다** — `AGENTS.md` 의 `Verify (앱 조작)` 줄에 검증 스킬이 등록돼 있으면 그 스킬로 앱을 직접 조작해 확인하고, 사람 눈이 필요한 것만 남깁니다. 계획에 `(BASE 대조)` 가 붙은 task 는 작업 전 코드에서 같은 시나리오가 실패하고 작업 후 통과해야 통과로 칩니다.
- **완료 보고**에는 시작·완료 시각과 소요 시간, 알아서 정한 것(「판정」 — 틀렸을 때 치를 대가 포함), 당신이 결정할 것(「승인 필요 항목」 — 권장안과 답하지 않으면 남는 것)이 나옵니다.
- 할 일이 많아 **회차를 나눴으면** 다음 회차 착수용 프롬프트가 코드블록으로 함께 나옵니다 — 새 세션에 그대로 붙여 넣으면 이어집니다.

**미뤄 둔 일은 대장에 모입니다.** 작업 중 "다음에 하자"고 미룬 항목은 커밋되는 대장(`docs/plans/deferred.md`)에 쌓이고 다음 계획 때 자동으로 조회됩니다. 대장으로 옮기지 못한 항목 수는 세션 시작 때 알려 주고, 같은 항목은 두 번 올라가지 않습니다. 대기가 많이 쌓이거나 가장 오래된 항목이 30일을 넘으면 다음 계획에 정리 작업이 자동으로 들어갑니다. 구현된 항목은 대응 커밋을 지목해 지우고, 기각한 것만 이유와 함께 `deferred-closed.md` 에 남습니다.

### 안전장치 (항상 작동)

작업 흐름과 별개로, **위험한 명령은 자동으로 차단**됩니다. 이건 끌 수 없습니다.

- 파일 전체 삭제(`rm -rf /`·`rm -rf ~/*` 등 홈·시스템 루트와 그 내용물 글롭), git 히스토리 파괴 — 강제 push 는 막되, 에이전트가 만든 karina/ 접두 브랜치를 이름으로 지정한 `git push --force-with-lease origin karina/<이름>` 만은 통과시킵니다(브랜치를 생략하거나 main 이 섞이면 막습니다)
- **DB 데이터 삭제·변조**: 전체 삭제(`DELETE` WHERE 없이), 전체 변조(`UPDATE` WHERE 없이), `DROP`/`TRUNCATE`, ORM 대량 삭제 등
- 단, `WHERE 조건`이 있는 일상적인 DB 작업은 그대로 통과합니다

## 단순 작업은 빠르게

모든 작업에 거창한 절차를 강제하면 오히려 불편합니다. 그래서 **3줄 이내의 단순 수정**은 계획 없이 바로 처리합니다:

- UI 문구·라벨 변경, 색상·아이콘 교체
- 오타·주석 수정
- 단일 라인 설정·리소스 변경

기준은 "3줄 이내 + 새 함수/구조 추가 없음 + 의도가 명확"입니다. 이 경우에도 다른 파일에 영향이 가면 자동으로 알려줍니다. 다만 한 요청 안에서 이런 작은 수정이 **파일 3개**째 또는 4회째에 이르면, 나눠 고치는 큰 변경일 수 있어 바로 수정할지 계획부터 세울지 묻습니다.

| 계획 수립 (`karina:plan`) | "기능 추가", "리팩토링", 여러 곳을 고치는 요청 | 요구를 1문1답으로 확정하고 영향 범위를 실측해 `plan.md` 를 쓴 뒤, 리뷰를 거쳐 승인받습니다. 파일 2개 이하의 작은 변경은 짧은 계획으로 승인 한 번에 끝냅니다 |

| 계획 체인 (`karina:chain-plan`) | "plan 1: …, plan 2: …" 처럼 계획 여러 개를 차례로 · "plan N부터" 재개 | 계획 여러 개를 한 번에 승인받고, Karina 앱 워커 탭(새 세션)에서 하나씩 계획→구현까지 진행합니다 — 아래 「계획 체인 자세히」 참고 |
| 디버깅 (`karina:karina-systematic-debugging`) | "버그", "에러", "안 됨" 등 | 근본 원인부터 찾고 회귀 테스트와 함께 고칩니다. 한 파일만 고치면 될 때는 「바로 수정 / 계획부터」를 한 번 묻습니다. GitHub 원격·`gh` 인증이 있으면 PR 을 엽니다 |
| 위키 운영 (`karina:llm-wiki`) | "위키에 등록/업데이트" | 프로젝트 지식을 쌓고 다음 작업 때 참조 |
| PR 운영 (`karina:pr`) | "PR 지켜봐" · "CI 초록 될 때까지" · "리뷰 코멘트에 답해" · "검증하고 머지해" | **babysit** — CI 실패 중 그 PR 의 코드 실패만 고치고 리뷰 코멘트에 답한 뒤 merge 가능한 상태에서 멈춥니다. **ship** — 코드를 쓰지 않은 검증 에이전트(`pr-verifier`)가 PASS 를 낸 뒤에만 squash merge 합니다. 화면이 바뀐 PR 은 사용자가 「PR <n> 화면 확인함」이라고 답해야 merge 합니다. 상한 인상·면제 추가 같은 게이트 완화가 있으면 작성자가 아닌 쪽의 서명 뒤에만 merge 합니다 — 체인의 계획 PR 은 코디네이터가, 그 밖(체인 끝 PR 포함)은 사용자가 「PR <n> 게이트 완화 확인함」으로 서명합니다 |

| 프로젝트 사실 기록 (`karina:record-project-fact`) | "AGENTS.md에 기록" · "AGENTS.md 새로 만들어줘" 또는 hook 제안 수락 | 빌드·DB·테스트 방식을 AGENTS.md에 축적(재확인 줄이기) · 파일이 없으면 최소 골격으로 생성 |
| 검증 스킬 만들기 (`karina:create-verification-skill`) | `/karina:create-verification-skill` 직접 호출 | 앱을 사용자처럼 조작해 확인하는 검증 스킬(`.claude/skills/verify-앱이름/`)을 만들고, 실제로 한 번 돌려 성공하면 AGENTS.md 에 등록합니다 · 웹·CLI/TUI·HTTP 서비스·Windows 데스크톱 지원 |
| 검증 스킬 유지 (`karina:maintain-verification-skill`) | `/karina:maintain-verification-skill` 직접 호출 | 앱이 바뀐 뒤 검증 스킬을 다시 맞추고, 실제로 돌려 확인된 수정만 PR 하나로 냅니다(고칠 것이 없으면 PR 없음) |
| 형식 검증 스킬 만들기 (`karina:create-formal-verification-skill`) | `/karina:create-formal-verification-skill` 직접 호출 | 테스트로 잡기 어려운 핵심 속성 하나(동시성·재시도·상태 기계·파서)를 TLA+ 같은 도구로 형식 검증하는 스킬을 만들어 등록합니다. 이후 그 코드를 건드리면 검사를 다시 돌립니다 · 도구 설치는 승인 후에만 |
| 형식 검증 스킬 유지 (`karina:maintain-formal-verification-skill`) | `/karina:maintain-formal-verification-skill` 직접 호출 | 코드가 바뀐 뒤 형식 검증을 코드에 다시 맞추고, 검증 쪽 어긋남과 실제 코드 버그를 구분해 보고합니다. 확인된 수정만 PR 하나로 냅니다(도구가 없으면 설치하지 않고 중단) |
| 세션 회고 (`karina:reflect`) | `/karina:reflect` 직접 호출 | 현재 세션 대화를 돌아보고 karina 스킬·hook 개선 후보를 표로 보여 준 뒤, 사용자가 고른 것만 Deferred 대장에 기록합니다(스킬 파일은 고치지 않음) |
| 계획 초안 (`karina:plan-draft`) | `/karina:plan-draft [요청]` 직접 호출 | 다른 세션이 plan.md 로 작업 중일 때 쓰는 별도 계획입니다. 요청을 주면 `karina:plan` 과 같은 인터뷰·실측·리뷰를 거친 계획을 plan.md 대신 레포 루트 plans/drafts 폴더에 초안으로 저장합니다(git 에는 올라가지 않음). 요청 없이 부르면 초안 목록(작성일·작성 이후 커밋 수)에서 골라 진행·수정·삭제합니다. 진행하면 plan.md 가 사용 중인지 먼저 확인하고, 비어 있으면 `karina:plan` 으로 다시 검토·승인받아 plan.md 로 올린 뒤 초안을 지웁니다 |
| 주석 정리 (`karina:no-comments`) | `/karina:no-comments [경로…]` 직접 호출 | 지정한 파일 전체(없으면 base 브랜치 대비 diff)의 코드 주석을 별도 리뷰어가 판정하고, 남길 근거가 없는 주석을 지웁니다. 주석이 감추던 결함 중 죽은 경로·안 쓰는 파라미터·우회 코드는 바로 고치고, 나머지는 설계를 보여 승인받은 뒤 고칩니다. 지운 주석의 이유는 커밋 본문용 문단으로 보고합니다(커밋은 하지 않음) |
| 임시 폴더 정리 (`karina:temp-cleanup`) | `/karina:temp-cleanup` 직접 호출 | `%TEMP%\karina-plugin\` 의 항목을 폴더별 표(크기·날짜)로 보여 주고, 고른 것만 시험 실행으로 확인받은 뒤 지웁니다. 자동으로 지우지 않는 백업도 여기서 지우며, 실행 중일 수 있는 체인 잠금은 지우지 않습니다 |

**계획 체인 자세히**

- **필요 조건**: Karina 앱이 떠 있고 이 세션이 Karina 앱 탭 안에 있어야 합니다. 워커 세션은 **agent 권한 확인을 끈 채** 돕니다 — 하니스 차단 hook 은 그대로 동작하지만 사람이 보는 권한 확인 층은 없습니다.
- **진행**: 계획마다 영향 범위를 먼저 실측하고 갈림길이 있으면 묻습니다. 체인 승인을 한 번 받으면 계획마다 새 워커 탭에서 계획→구현을 순서대로 진행합니다. 서로 의존하지 않고 파일도 겹치지 않는 계획은 각자 worktree 에서 동시에(기본 2개) 돌고, 끝난 순서대로 병합·검증됩니다.
- **승인 모드** (merge 는 사용자가 `karina:pr` 로 요청할 때):
  - `Y` — 계획 사이를 로컬 커밋으로 잇고, 체인이 끝나면 PR 하나를 엽니다(GitHub 원격·`gh` 로그인이 있을 때).
  - `P` (PR 모드) — 계획마다 PR 을 열어 CI 초록·`pr-verifier` PASS 뒤 squash merge 하고 다음 계획으로 넘어갑니다.
  - `T` (스택 모드) — 계획마다 PR 을 앞 PR 위에 쌓고, 끝에 스택 전체를 「스택 화면 확인함」 한 번으로 확인받아 merge 합니다.
  - `P`·`T` 는 GitHub 원격·`gh` 로그인과 미커밋 변경·미반영 커밋이 없는 브랜치가 필요합니다(`T` 는 병렬 그룹이 없을 때만).
- **사용자에게 오는 질문**: 태그·릴리즈 같은 별도 승인, 사용자가 답한 것을 뒤집는 것, 요청 범위 변경, 기존 것(DB 데이터·명령·설정·파일 형식·화면 동작)을 깨는 변경, 뒤 계획이 전제로 쓰는 화면 갈림길만 묻습니다. 그 밖의 워커 질문은 코디네이터가 판정하고 근거·되돌리는 법을 체인 보고에 남깁니다. 답이 늦으면(기본 30분) 범위를 넓히지 않는 기본값으로 진행합니다 — 실행 승인과 기존 것을 깨는 변경은 계속 기다립니다.
- **멈춤·재개**: 실행 중 「멈춰」라고 하면 멈추고, 「plan N부터」로 이어 갑니다. 같은 실패가 3번 반복되거나 merge 가 막히면 PR 을 열어 둔 채 멈춥니다. 코디네이터 컨텍스트가 압축돼도 Karina 앱 기록에서 진행 상태를 되찾습니다.
- **보고**: 체인 보고에 코디네이터 판정, 워커가 돌린 검증, 남은 워커 탭, 환경 개선 후보(AGENTS.md·Deferred 대장·플러그인·위키)가 실립니다.

### Subagents

작업을 직접 하는 Claude와 **별개의 검토자** 둘이 결과를 점검하고, PR 을 merge 할 때는 **독립 검증자** 하나가 PR head 를 직접 돌려 봅니다. 위키 세션에서는 **작성 담당** 하나가 페이지 작성을 나눠 맡습니다. 작성자와 검토자를 분리해 "자기 일을 자기가 검토하는" 맹점을 줄입니다.

| 검토자 | 모델 | 언제 | 무엇을 |
|---|---|---|---|
| plan-reviewer | Opus | 계획 완성 후(최대 3라운드 · 경량 계획에서는 생략) · 따지기로 task 나 완료 조건이 바뀌면 1회 더 | 계획이 **실측 위에 서 있는지** — 적힌 명령이 주장을 뒷받침하는지, 바꿀 심볼의 호출자가 빠지지 않았는지, 승인 항목을 피할 다른 설계가 있는지, 검증 명령이 `AGENTS.md` 에 있는지 |
| completion-reviewer | Opus | 모든 task 완료 후 1회(경량 계획은 변경이 3파일 이상일 때만) | 계획과 최종 결과의 대조 — 요구가 반영됐는지, 완료 표시가 사실인지(검증 명령을 표본으로 다시 돌림), 성공 기준이 실제로 참인지 |
| pr-verifier | Opus | `karina:pr` ship 이 merge 하기 전 PR 마다 1회 | PR head 를 받은 worktree 에서 빌드·테스트·검증 스킬을 돌리고, 화면 시나리오는 PR 전 코드와 비교합니다. 체크를 끄는 변경은 FAIL, 상한 인상·면제 추가는 게이트 완화 줄로 따로 냅니다. 한 명령이 실패해도 끝까지 돌려 실패를 전부 나열합니다. 결과는 PASS / PASS+NOTES / FAIL — 코드를 쓰지 않은 쪽의 판정만 merge 근거가 됩니다 |
| reflect-reviewer | Opus | 사용자가 `/karina:reflect` 를 부를 때 1회 | 세션 전사를 읽고 karina 스킬·hook 의 개선 후보 표를 냅니다(파일은 고치지 않음) |
| comment-reviewer | Opus | 사용자가 `/karina:no-comments` 를 부를 때 1회(판정을 거부하면 1회 더) | 지정 범위의 코드 주석을 지울 것·남길 것·코드로 고칠 대상·제약 주석으로 판정한 표를 냅니다(파일은 고치지 않음) |

**검토자는 정해진 자리에서만 부릅니다** — task마다 부르지 않습니다. Claude Opus 5는 지시 없이도 자기 작업을 검증하므로, 그 위에 검토 단계를 얹으면 비용과 시간만 늘고 품질은 오르지 않습니다([Anthropic 프롬프팅 가이드](https://platform.claude.com/docs/ko/build-with-claude/prompt-engineering/prompting-claude-opus-5)의 권고).

검토 흐름의 규칙:

- **검토자는 읽기만 합니다** — 지적을 반영하는 것은 Claude 본체입니다. 검토와 수정의 주체를 나눠야 "자기가 쓴 것을 자기가 통과시키는" 경로가 막힙니다.
- **심각도로 걸러 내지 않습니다** — 전부 보고하게 하고, 무엇을 고칠지는 호출한 쪽이 정합니다.
- **확신이 낮은 지적도 냅니다** — `(판정 유보)` 표시를 붙이되, 근거 없는 인상만 남는 지적은 적지 않습니다.
- **검토자가 호출되지 않는 환경**이면 그 사실을 보고에 적고 진행합니다 — 리뷰 부재를 통과로 적지 않습니다.

| 작성 담당 | 모델 | 언제 | 무엇을 |
|---|---|---|---|
| wiki-page-writer | Sonnet (effort high) | 위키 세션이 작성할 페이지가 3개 이상이고 겹치지 않게 나눌 수 있을 때 | 배정받은 위키 페이지만 소스 코드를 읽어 작성합니다. 인덱스·로그 같은 공유 파일과 커밋은 위키 세션 본체가 맡습니다 |

모델과 effort 를 정의에 고정한 이유는, 이름 없이 부르면 본체의 모델(Opus)과 effort 를 그대로 물려받기 때문입니다 — 범위가 정해진 대량 작성이라 Sonnet 이면 충분합니다.

### Hooks (자동 안전망)

당신이 신경 쓰지 않아도 **자동으로 작동**하는 장치들입니다.

**차단하는 것**

- **위험한 명령** — 위 「안전장치」의 파일 전체 삭제·히스토리 파괴·DB 대량 삭제 (끌 수 없음)
- **안전장치 자체의 개조·삭제** — 설치된 hook 스크립트·설정·규칙 파일을 고치거나 지우는 시도 (끌 수 없음). 규칙 파일을 읽지 못하면 화면에 알리고, 이 플러그인을 개발하는 저장소에서는 적용되지 않습니다
- **커밋 속 자격증명** — 개인키, 아이디·비밀번호가 박힌 접속 URI, 인용부호로 감싼 아이디/비밀번호 쌍, 자격증명이 든 DB 연결 문자열이 새로 추가되면 커밋을 막습니다. 환경변수 참조(`$env:…`·`${…}`·`process.env.…` 등)는 막지 않습니다. 한 번에 50개가 넘는 파일을 스테이징하면 다 검사할 수 없어 막으니 커밋을 나눕니다. 오탐이면 사용자가 Claude Code 시작 전 터미널에서 `CLAUDE_HARNESS_ALLOW_SECRET=1` 로 우회합니다
- **AGENTS.md 에 맞지 않는 내용** — 진행 상태·"다음 작업" 같은 인계 서술(제목 형태)과 디렉터리 트리. 진행 상태는 `plan.md`, 구조는 위키에 둡니다
- **계획서를 스크립트로 고치기** — 계획서는 git 이 추적하지 않아 되돌릴 수 없으므로, 쓰는 명령만 막고 읽는 명령은 통과시킵니다
- **계획 없이 코드 쓰기**, 그리고 **계획서 체크박스를 갱신하지 않은 task 완료 커밋**

**경고·자동 처리하는 것** (막지 않음)

- **외부 작업 경고** — push·PR·병합은 「승인된 계획·스킬 안이면 진행, 아니면 승인」, 태그·릴리즈·배포는 「항상 승인」을 알립니다
- **시크릿 경고** — API 키·토큰·IP·`.env` 스테이징처럼 오탐 여지가 있는 것은 커밋할 때와 파일을 저장할 때 경고만 합니다(이미 커밋된 내용은 다시 경고하지 않음)
- **줄바꿈 경고** — CRLF 저장소에서 편집 도구가 LF 로 저장하면 알립니다
- **위험한 검색·삭제 경고** — `find /` 처럼 끝나지 않을 검색, `X=/; rm -rf $X` 처럼 변수에 담은 위험 경로 삭제
- **남은 콘솔 프로세스 정리** — 부모가 사라진 채 CPU를 먹는 `more`·`find` 를 세션 시작·종료 때 정리합니다(이벤트 로그에만 기록)
- **임시 파일 기한 정리** — 스킬이 `%TEMP%\karina-plugin\` 에 남긴 화면 변형·검증 증거·일회성 스크립트·체인 결정 파일 중 기한이 지난 것을 세션 시작 때 지웁니다. 백업은 지우지 않습니다(`/karina:temp-cleanup` 으로 직접 고릅니다)
- **자율 루프 이어 가기** — `karina:implement` 중 미완 task 가 남은 채 turn 이 끝나면 남은 task 번호와 함께 계속하라고 알립니다(같은 상태에서 최대 2회)
- **응답 언어 고정** — 사용자가 메시지를 보낼 때와 스킬이 발동될 때마다 「사용자에게 하는 답·보고는 한글로」 한 줄을 실어, 영문 스킬·도구 출력이 쌓인 긴 세션에서도 한글로 답하게 합니다
- **AGENTS.md 관리** — 계획 때 없으면 최소 골격으로 생성(저장 전 승인), 빌드·테스트·DB 명령을 실행하면 기록 제안, 크기 한도에 가까워지면 미리 알림
- **세션 컨텍스트 주입** — 세션 시작·재개·대화 요약 직후 `plan.md` 진행 상태, 위키 설정 상태, AGENTS.md 목차(또는 전문)를 실어 줍니다. 요약 직후에는 루프 제어·계획 규칙 원문도 다시 실어, 긴 작업에서 규칙이 사라지지 않게 합니다
- **위키 뒤처짐 알림** — 위키가 코드보다 30커밋·14일 이상 밀렸거나 미반영 항목이 있으면 작업 시작 때 한 줄로 알립니다(반영은 "위키 업데이트" 요청 때)
- **커밋 직전 문서 낡음 고지** — 하니스가 참고하는 문서가 실제와 어긋났으면 커밋할 때 알립니다
- 파일 인코딩·줄 수 검사, 변경 영향 경고
- **하니스 레포 전용** — 미뤄 둔 대장의 잔량·가장 오래된 항목, 설치본과 레포의 버전 차이·미배포 변경을 세션 시작 때 알립니다

> 명령 실행 때 도는 안전망은 한 프로세스로 묶여 빠르게 반응하고, 위험 명령 차단만은 따로 실행돼 영향을 받지 않습니다. 검사 모듈이 로드에 실패하면 조용히 통과하지 않고 경고합니다.

**차단/경고 이벤트 로그 (오탐 리뷰용)**: 차단·경고가 날 때마다 `~/.claude/.state/hook-events/{YYYY-MM}.jsonl` 에 한 줄씩 쌓입니다(90일 지난 파일은 자동 정리 · 시크릿이 든 명령은 원문을 남기지 않음). 정상 작업이 자꾸 막히면 Claude에게 "hook 이벤트 로그에서 최근 차단 내역 검토해줘"라고 요청하세요.

## 위키 연동 (선택 기능)

프로젝트 지식을 쌓아두고 재사용하는 기능입니다. **쓰려면 먼저 위키 폴더를 설정해야 하며, 설정하지 않으면 이 기능만 비활성화될 뿐 나머지 karina 기능은 정상 작동합니다.**

위키는 **Claude 가 읽는 지식 저장소**입니다 — 프로젝트 개요·기능 목록·결정 이력·재사용 패턴을 담고, 코드가 바뀌면 틀어지는 정보(파일 경로·수치·진행 상태)는 담지 않습니다. 사실마다 근거(`파일@커밋`)를 붙여, 근거 파일이 바뀌면 위키 점검이 「근거 낡음 가능」으로 알려 줍니다.

### 설정 방법 (최초 1회)

위키를 처음 쓸 때 폴더를 한 번만 지정하면 됩니다:

```
"이 프로젝트 위키에 등록해줘"   ← 이렇게 요청하면
   ↓
"LLM WIKI 폴더 경로를 알려주세요"  ← Claude가 경로를 물어봄
   ↓
경로 입력 (예: D:\MyWiki 또는 기존 Obsidian vault 경로)
   ↓
설정 완료 — 이후 다시 묻지 않음
```

- 설정한 경로는 PC의 개인 설정 파일(`~/.claude/llm-wiki-config.json`)에 저장됩니다. **plugin을 업데이트해도 유지**되며, 위키 내용도 plugin 밖 폴더에 있어 안전합니다.
- 위키 폴더를 옮기거나 삭제하면, 다음 사용 때 Claude가 새 경로를 다시 물어봅니다.
- **되돌리기**: 위키 폴더가 git 저장소면 여러 파일을 바꾸기 직전에 커밋을 남기고, 아니면 수정 전 사본을 `90_archive/backup/{날짜}/` 에 남깁니다. 잘못 갱신됐으면 "위키 되돌려줘"라고 하면 차이를 보여 주고 확인 후 되돌립니다(같은 시간에 Obsidian 에서 직접 고친 내용은 건드리지 않습니다).
- 폴더를 지정하지 않으면 위키 참조·저장 단계는 그냥 건너뜁니다 (계획·구현·검증은 정상 진행).

### 무엇이 기록되나 (큐 태그)

- **결정 이력 ([DECISION])**: 보류·기각한 기획과 그 번복이 그 프로젝트의 결정 이력(`decisions.md`)에 쌓입니다. 다음 계획 때 Claude가 먼저 확인해 예전에 기각한 것을 모르고 다시 논의하지 않고, "이 기능 왜 안 하기로 했지" 같은 질문에도 답합니다.
- **작업 함정 (레포 `docs/conventions.md`)**: 그 프로젝트에서 작업할 때 알아야 할 주의사항은 위키가 아니라 레포의 `docs/conventions.md` 에 코드와 같은 커밋으로 남습니다 — 브랜치·PC가 달라도 그 코드에 맞는 판이 보입니다. 같은 원인으로 두 번 막힌 것은 구현을 마칠 때 Claude가 적고, "이거 기억해둬"라고 하면 내용을 보여 주고 승인받아 적습니다.
- **증상별 인덱스 ([SYMPTOM])**: 디버깅에서 확정된 "증상 → 원인 → 해법" 매핑이 쌓여, 비슷한 증상을 만나면 출발점으로 씁니다(가설로만 쓰고 원인 확정은 현재 코드로 합니다).

### 쌓인 지식을 다루는 방식

- **재사용 지식 우선**: 한 프로젝트에서 겪었어도 그 스택·코드에 묶이지 않는 지식은 범용 패턴으로 올립니다.
- **미등록 프로젝트 자동 등록**: 계획을 세울 때 위키에 없는 프로젝트는 묻지 않고 등록합니다. 내 커밋이 없는 참고용 저장소와 스택 표식이 없는 프로젝트(셸 스크립트 모음 등)는 건너뜁니다 — 직접 요청하면 등록합니다.
- **저장소 주소로 식별**: PC·폴더 이름·프로젝트 이름이 바뀌어도 같은 프로젝트로 알아봅니다.
- **뒤처짐 표시**: 위키가 저장소를 따라오지 못하면 페이지 맨 위에 경고를 달고, 작업 전에 참고할 때는 Claude가 직접 다시 확인합니다.
- **공용 레시피 역방향 갱신**: 기능 문서에 연결된 공용 레시피는 그 기능을 개선하면 함께 갱신됩니다.
- **질문 답변**: 결론 → 상세 → 출처 순으로 답하고, "그동안 무슨 변화가 있었지" 같은 질문은 결정 이력·작업 로그를 시간순으로 엮어 답합니다.

### 파일이 커지면 (자동 정리)

- 위키 페이지·기록 파일이 크기 한도에 닿으면 점검 도구가 **알아서** 오래된 기록은 보관 폴더로, 긴 절은 하위 문서로 옮기고 그 자리에 안내 한 줄을 남깁니다. **요약하거나 지우지 않고 위치만 옮기며**, 실패했을 때만 알립니다.
- 안내 줄이 가리키는 문서와 절 이름이 실제로 있는지도 점검합니다.
- `AGENTS.md` 가 세션 주입 상한에 닿으면 큰 절을 다른 문서로 옮깁니다(빌드·테스트 명령과 금지 항목은 항상 남습니다). 옮길 것이 없으면 「AGENTS.md 정리해줘」로 줄이는 방법을 안내하며, 이 정리는 계획을 보여 주고 승인받은 뒤에만 합니다.

### 사용 흐름

```
1. (설정 후) "이 프로젝트 위키에 등록해줘"
   → 프로젝트를 분석해 지식 정리

2. 이후 작업할 때 (자동)
   → 계획·디버깅 단계에서 위키의 과거 기록을 참조
   → "예전에 비슷한 걸 했었지" 하고 재조사를 줄임

3. 작업 끝나면
   → 위키에 남길 내용(기능 변경·개선 교훈)이 있으면 반영할지 물어봄
```

> 위키는 Obsidian 같은 마크다운 도구로 열 수 있는 폴더이고, 기존 vault 를 그대로 써도 됩니다. 형식은 공개 지식 표준인 **OKF(Open Knowledge Format) v0.2** 와 맞춰져 있어 다른 도구와 지식을 교환하기 쉽습니다.

- **인덱스 자동 생성**: 첫 화면의 프로젝트·기능·가이드 목록은 각 문서에서 자동으로 만들어지므로 손으로 맞출 필요가 없습니다. 손으로 쓴 구역(증상별 인덱스 등)은 그대로 보존됩니다.
- **자동 커밋**: 위키 폴더가 git 저장소면 작업마다 커밋하고 세션 끝에 한 번 push 합니다(코드 저장소는 종전대로 확인을 거칩니다). git 이 아니면 쌓인 백업 사본을 이전 날짜 것부터 자동 정리합니다(삭제·복구 직전 사본은 보존).
- **화면 출력**: 진행 중에는 `📚 위키: B(ingest) — 프로젝트명` 같은 한 줄만 나오고, 끝나면 바뀐 파일마다 한 줄씩 보고합니다.
- **위키 점검(lint)**: 링크·분량·인덱스·각주 경로·시크릿 유입 등 30여 항목을 기계로 검사합니다. 코드 작업 중 위키와 코드가 어긋난 것을 발견하면 대기 목록(pending)에 남겨 다음 위키 갱신 때 챙깁니다.

| 단순 코드 | 한 파일·한 메서드 | 가벼운 검토 |
| 일반 코드 | 2-3 파일, 호출처 갱신 | 표준 검토 |
| 복잡/광범위 | 다중 파일, 시그니처 변경 | 전체 검토 |

</details>

<details>
<summary>공식 Claude Code 기능과의 관계</summary>

karina는 Claude Code 내장 기능을 **대체하지 않고 보완**합니다.

`/code-review`, `/security-review`: karina는 **작성 중** 계획 준수를 검증하고, 공식 기능은 **PR 단계**에서 버그·보안을 점검합니다. 둘 다 쓰면 이중 점검이 됩니다.

권장 흐름: `karina로 작성·검증 → 회차 끝 PR 자동 생성 → 공식 /code-review로 재점검 → karina:pr ship 으로 독립 검증 뒤 merge`

</details>

<details>
<summary>AGENTS.md란</summary>

프로젝트의 빌드·테스트 명령과 규칙을 담은 파일입니다. karina가 작업할 때 이 파일을 참조합니다. 없으면 생성을 제안하며, 직접 작성할 수도 있습니다.

karina는 **특정 언어 전용이 아닙니다.** 빌드·테스트 명령은 **한 번 실행해 통과한 것만** 적으므로 언어를 가리지 않고, 확인하지 못한 값은 비워 둡니다 — 추측치를 미리 박아 넣지 않는 쪽이 다음 세션을 오도하지 않습니다. karina의 계획·검증·자율 루프도 언어를 가리지 않습니다.

**생성된 AGENTS.md는 그대로 써도 동작하지만, 프로젝트 스타일에 맞게 다듬으면 더 좋은 성능을 냅니다.** 빈 칸을 채우고 프로젝트 고유의 규칙·함정·컨벤션을 추가할수록 Claude가 추측을 줄여 더 정확하게 작업합니다. 빌드·테스트 명령으로 시작해 점진적으로 보강하는 것이 기본 동작이며, 빌드·테스트·DB 명령을 실행할 때마다 기록 제안이 따라옵니다.

</details>

## 설치 관리

```powershell
# 업데이트
claude plugin marketplace update karina-plugins
claude plugin update karina@karina-plugins

# 제거
claude plugin uninstall karina
claude plugin marketplace remove karina-plugins
```

<details>
<summary>배포 워크플로</summary>

설치는 GitHub 마켓플레이스 경로 하나뿐입니다 — 로컬 폴더에서 직접 설치하지 않습니다. 개발은 jongcheol-pak/Karina-Plugins 의 plugins/claude-harness-karina/ 폴더에서 세션을 열고 합니다(레포 루트에서 열면 하니스 판정 hook 이 꺼집니다). 수정은 커밋 → push → 아래 흐름으로 배포한 뒤 사용 PC에서 업데이트합니다.

```powershell
# 배포 (개발 PC에서 수정 후) — 회차 PR 이 merge 되면 karina:pr ship 이 merge 뒤 버전 커밋을 main 에 바로 push 한다
# 그 버전 커밋으로 릴리즈 발행(별도 승인): gh release create karina-v<버전> --target <버전 커밋 full-sha>
# → 사용 PC에서 위의 "업데이트" 명령 실행
```

</details>

<details>
<summary>구버전 캐시 회수</summary>

`/plugin update`는 버전마다 `~/.claude/plugins/cache/karina-plugins/karina/<버전>/` 을 새로 만들고 예전 것을 지우지 않아 캐시가 단조 증가합니다. 회수는 손으로 합니다 — 그 폴더 아래에서 **지금 설치된 버전 폴더를 뺀** 예전 버전 폴더를 지웁니다.

**설치본 버전 폴더는 지우지 않습니다** — 지금 돌고 있는 세션의 hook이 그 폴더에 살아 있어, 지우면 그 세션의 안전장치가 통째로 사라집니다. 설치본 버전은 `claude plugin list` 로 확인합니다. 회수한 구버전이 다시 필요하면 GitHub 태그에서 재설치합니다.

</details>

## 트러블슈팅

<details>
<summary>plugin 명령이 안 보여요</summary>

Claude Code를 재시작하거나 `/reload-plugins`를 실행하세요. 그래도 안 되면 `claude plugin enable karina@karina-plugins`로 활성화 상태를 확인하세요.

</details>

<details>
<summary>안전장치(hook)가 너무 자주 막아요</summary>

하니스의 hook은 항상 켜져 있어 끌 수 없습니다. 정상 작업인데 막혔다면, 계획(plan)을 먼저 만들거나 명령을 더 구체적으로(예: 삭제 명령에 `WHERE 조건` 추가) 바꾸면 통과합니다. 위험한 명령 차단(파일 삭제·DB 삭제 등)은 안전을 위한 것이니, 정말 필요한 작업이면 더 좁은 범위로 나눠 실행하세요.

> 다음 정상 작업들은 계획 없이 통과합니다 — 임시 폴더 정리(`$env:TEMP\...` 하위 — `Join-Path`로 조립한 하위 폴더 경로 포함), 프로젝트 내 단일 파일 `chmod +x`, 현재 폴더 상대 정리(`Get-ChildItem . -Recurse | ...`), **상위 폴더 정리(`rm -rf ../build` 류)**, 테스트/재현용 신규 파일(tests/·`repro*`, 30줄 이하), 마크업·스타일 파일(`.xml`/`.html`/`.css`). 위험 차단(홈·시스템 삭제, DB 파괴 등)은 그대로이며, 여기에 **경로가 상위로 올라가기만 하다 끝나는 형태**(`..`가 연달아 이어져 드라이브 루트에 닿는 것)와 **루트 전체 글롭**이 포함됩니다.
>
> 알려진 한계: 인자가 3개 이상인 경로 조립(`Join-Path a b c`)은 아직 커버하지 않아 막힐 수 있습니다 — 그때는 경로를 한 문자열로 이어 쓰면 통과합니다.

</details>

<details>
<summary>한글이 깨져요</summary>

PowerShell 인코딩 문제일 수 있습니다. karina의 모든 스크립트는 UTF-8(BOM)로 저장되어 있으니, Claude Code와 터미널이 UTF-8을 쓰는지 확인하세요.

</details>

<details>
<summary>구현이 중간에 멈췄어요</summary>

"T<N>부터 계속"이라고 말하면 승인된 계획서의 그 task부터 마지막 task와 최종 검증까지 이어서 진행합니다. 계획서의 체크박스가 진행 상태의 기준이라 끝난 task는 다시 하지 않습니다.

</details>

<details>
<summary>계획 없이 고치려는데 편집이 막혀요</summary>

계획이 없으면 3줄을 넘는 수정은 첫 편집부터, 3줄 이내의 작은 수정은 한 요청 안에서 서로 다른 파일 3개째 또는 4번째 편집부터 안전장치가 막습니다. 한 파일만 고치면 되는 일이면, 계획이 필요한지 묻는 화면에서 바로 수정을 고르세요 — 그 파일 편집이 통과합니다. 고칠 곳이 여럿이면 계획을 먼저 세우는 것이 정상 경로입니다.

</details>

<details>
<summary>업데이트했는데 바뀐 동작이 안 보여요</summary>

「설치 관리」의 업데이트 두 줄(`claude plugin marketplace update karina-plugins` → `claude plugin update karina@karina-plugins`)을 차례로 실행한 뒤 Claude Code를 재시작하거나 `/reload-plugins`를 실행하세요.

</details>

<details>
<summary>화면 확인을 매번 저한테 넘겨요</summary>

`/karina:create-verification-skill` 을 한 번 돌려 검증 스킬을 만드세요. 실행 증명을 통과하면 그 스킬이 `AGENTS.md`의 `Verify (앱 조작)` 줄에 경로를 적습니다. 구현이 화면 확인을 넘기기 전에 그 스킬로 먼저 조작하고, 그래도 사람 눈이 필요한 것만 완료 보고에 남깁니다.

</details>

<details>
<summary>동시성·재시도 버그가 테스트로 안 잡혀요</summary>

`/karina:create-formal-verification-skill` 을 돌리세요. 테스트로 잡기 어려운 핵심 속성 하나(동시성·재시도·상태 기계·파서)를 골라 형식 검증하고 `AGENTS.md`의 `Verify (형식 검증)` 줄에 등록합니다. 그 뒤로 구현·PR 검증·디버깅이 그 코드를 건드릴 때마다 검사를 다시 돌립니다. 검증 도구(예: TLA+)는 승인을 받은 뒤에만 설치합니다. 코드가 많이 바뀌었으면 `/karina:maintain-formal-verification-skill` 로 검증을 코드에 다시 맞춥니다.

</details>

## 호환 환경

karina는 두 부분으로 나뉘며, OS 의존성이 다릅니다.

| 구성 | OS 의존 | 설명 |
|---|---|---|
| **Skills · Subagents** (계획·구현·디버깅·검증 로직) | OS 무관 | 지침(markdown)이라 어디서나 동작 — 단 `chain-plan` 은 Karina 앱(Windows)와 python 3 이 필요하다 |
| **Hooks** (위험 명령 차단·권한/보안 변경 차단·외부 작업(push·릴리즈) 경고·민감정보 경고·plan 강제 등 자동 안전망) | **pwsh 7 우선·5.1 폴백** | hook 스크립트는 Claude Code가 띄운 PowerShell에서 직접 실행(자식 셸 재기동 없음). 실행 셸은 Claude Code의 powershell 해석을 따르며(실측: pwsh 7 있으면 `pwsh` 우선), 스크립트는 내장 powershell.exe(5.1) 호환을 유지; macOS/Linux는 `pwsh` 7 |

| 항목 | 지원 |
|---|---|
| OS | **Windows 10/11**: 완전 지원·검증. **macOS/Linux**: pwsh 7 설치 시 동작하도록 구현됐으나 **실제 환경 미검증(실험적)** |
| 런타임 | **Windows**: 추가 설치 불요 — 실행 셸은 Claude Code가 결정(실측: pwsh 7 있으면 그쪽 우선), 스크립트는 내장 powershell.exe(5.1) 호환 유지. **macOS/Linux**: pwsh 7 필요(`brew install powershell` 등) |
| Claude Code | **최소 v2.0** (플러그인 사용) · AGENTS.md 직접 로드는 v2.1.277+ (미만이면 세션 시작 hook 의 Read 지시가 대신) · **하니스 개발(eval 러너)은 권장 v2.1.269+** — `--filter` 이름 검증과 골든 러너 병렬 모드가 안정된 판이다. 미만에서는 부분 실행 필터가 조용히 0건을 돌 수 있다 |
| 대상 언어 | **모든 언어 동작** — .NET, Android, Node/TS, Python, Go, Rust는 표식 파일로 자동 감지·자동 설정. 그 외(Flutter·Swift·Java·C++·Ruby 등)는 빌드/테스트 명령만 입력하면 동일하게 작동 |

> **요약**: 자동 안전망(hook)은 OS에 무관하게 동작하도록 구현됐습니다. **Windows는 검증 완료** — pwsh 7이 있으면 그쪽에서, 없으면 내장 powershell.exe(5.1)에서 동작해 **추가 설치 없이 안전망이 항상 동작**합니다. **macOS/Linux는 pwsh 7 필요·실험적(미검증)** 입니다(`brew install powershell` 등).

## 설계 철학

- **재작업 방지 > 토큰 절약**: 검증에 드는 비용은 잘못 만든 걸 다시 만드는 비용보다 쌉니다.
- **계획은 함께, 구현은 자동**: 방향은 사람이 정하고, 실행은 Claude가 끝까지.
- **확실한 안전망**: 검토는 확률적이지만, 위험 명령 차단 같은 hook은 결정적으로 작동합니다.
- **읽히는 문장**: 완료 보고·계획 승인 요약·커밋 메시지·PR 본문·README·디버깅 보고·체인 보고·PR 운영 보고·검증 스킬 보고는 `skills/WRITING.md` 의 한글 문체 규칙(군더더기·번역투·피동 남용·과압축을 줄이고 느낌 대신 동작과 수치로 쓴다)을 따릅니다.
